# Участие в разработке

mcprig — проект до 1.0 с одним оператором. Источник истины — Gitea
(`sintez/mcprig`), GitHub (`akrhin/mcprig`) зеркалит архивы релизов.

Прочитать до первой правки: `AGENTS.md` (правила репозитория),
`docs/CURRENT-GOAL.md` (этап и его ворота), `docs/ru/development.md` (сборка,
тесты, стенд). Поведение берётся из `docs/reference/ts-manager-contract.md`;
правка, которая ему противоречит, требует записи в `docs/decisions/`.

## Что куда

| Что | Куда |
| --- | --- |
| ошибка или предложение | issue здесь |
| проблема безопасности | лично владельцу, не публичным issue |
| вопрос по установке | сначала документация: `docs/ru/` |
| правка | pull request из ветки, не коммит в `master` |

## Issue

Одна проблема — один issue; сначала поищи среди закрытых.

- Заголовок: `область: что не так`, например
  `sandbox: на alpine нет prlimit, падает каждый сервер в песочнице`.
  Области: `panel`, `set`, `stdio`, `sandbox`, `config`, `cli`, `docs`,
  `docker`.
- В теле: что случилось, что ожидалось, как воспроизвести (команды и конфиг,
  где секреты заменены на `<token>`), версия (`mcprig --version` или тег
  образа) и точная строка ошибки. Тексты ошибок русские и ищутся по коду —
  вставляй как есть, не перепечатывай.
- Форма issue спрашивает эти поля; issue без версии и строки ошибки
  возвращается за ними.

## Pull request

- Ветка: `<префикс>/<короткое-имя>`, например `openchamber/panel-isolation`.
- Коммиты: Conventional Commits с русским заголовком —
  `type(scope): subject`. Типы: `feat`, `fix`, `docs`, `test`, `refactor`,
  `perf`, `chore`, `release`. Один коммит — одно осмысленное изменение.
- Заголовок PR = изменение одной строкой, в той же форме, что коммит: Gitea
  делает из него merge-коммит.
- Тело PR: что изменилось и зачем, какие ворота прогнаны и с каким
  результатом, какие доки и changelog тронуты, `Closes #N`.
- `git commit` без `--no-verify`: хук собирает дерево и гоняет тесты.

Ворота перед push:

```bash
gofmt -l .                          # должно быть пусто
go build ./...
go vet ./...
go test ./... -race -count=1 -p 1   # -p 1 обязателен
```

`-p 1` не опция: `internal/manager` и `e2e` поднимают настоящие наборы в общем
диапазоне 9100–9199 и отбирают порты друг у друга при параллельном прогоне.
Контрактный набор идёт против живого панельного сервера:

```bash
E2E_BASE=http://127.0.0.1:9091 ./scripts/contract-e2e.sh
```

Правка поведения обновляет `docs/en/` и `docs/ru/` вместе и добавляет строку в
`CHANGELOG.md` под `## [Unreleased]`. Если обновлять нечего — так и написать в
теле PR.

## Код

- Go в стандартном стиле; новая зависимость требует причины в PR.
- Комментарий объясняет «почему», которого не видно в коде, одной строкой.
- Нетривиальная логика — ветвление, цикл, парсер, всё, что касается токенов,
  авторизации или песочницы, — приходит с тестом.
- Дефекты TypeScript-эталона — требования к исправлению, а не поведение для
  копирования: ни одна строка TypeScript сюда не переносится.

## Версионирование

[SemVer](https://semver.org/), `MAJOR.MINOR.PATCH`, в git-теге `vX.Y.Z`.
Версия берётся только из тега: goreleaser подставляет её через
`-X main.version={{ .Version }}`, сборка из исходников печатает `dev`, а
`mcprig --version` (и версия в панели) показывает, что несёт бинарник. В дереве
константы версии нет — вручную поднимать нечего.

До 1.0 числа значат:

| Изменение | Инкремент |
| --- | --- |
| исправление, при котором контракт, ключи конфига и схемы мета-инструментов не меняются | `PATCH` |
| новый мета-инструмент, ключ конфига, флаг, экран панели или поведение, которое оператор заметит | `MINOR` |
| ломающее изменение — переименованный или убранный ключ, несовместимый контракт мета-инструментов или `/mcp`, изменённый дефолт авторизации | `MINOR` до 1.0, `MAJOR` после |
| доки, тесты, CI, рефакторинг без наблюдаемого изменения | `PATCH` или релиза нет вовсе |

Ломающее изменение едет в `MINOR` только пока проект до 1.0, и оно обязано
сказать об этом в своей секции changelog и нести заметку о миграции. После 1.0
ломающих изменений в миноре нет.

Теги образов следуют релизу: `X.Y.Z-slim` и `X.Y.Z-full`, плюс `latest` и
`latest-full` на самый свежий релиз — никогда на ветку.

Правила:

- Тег ставится на коммит `release: vX.Y.Z`, который переносит
  `## [Unreleased]` в `## [X.Y.Z] - YYYY-MM-DD` и оставляет `Unreleased`
  пустым. В этом коммите больше ничего нет.
- Опубликованный тег не переносится и не удаляется; сломанный релиз получает
  новый `PATCH`.
- `CHANGELOG.md` — единственный источник release notes: Added / Changed /
  Fixed / Removed / Security, важное выше.

## Образы

Два образа, `slim` и `full` (см. [docs/ru/install.md](docs/ru/install.md)), лежат
в реестре Gitea проекта как `sintez/mcprig`.

Руками:

```bash
reg=frosty-ad-gt.cloudpub.ru/sintez/mcprig
ver=$(git describe --tags --abbrev=0 | sed 's/^v//')
for target in slim full; do
  docker build --target "$target" --build-arg VERSION="$ver" \
    --build-arg REVISION="$(git rev-parse --short HEAD)" -t "$reg:$ver-$target" .
  docker push "$reg:$ver-$target"
done
```

Задача на тег `v*` делает то же самое и вдобавок ставит `latest` (slim) и
`latest-full`. Ей нужны секреты `REGISTRY`, `REGISTRY_USER` и
`REGISTRY_PASSWORD`; без них она печатает, что пропустила шаг. Задача идёт до
публикации черновика релиза, поэтому `latest` сдвигается на теге; если черновик
так и не опубликовали, `latest` указывает на неопубликованную версию — переназначь
две метки руками:

```bash
for pair in "slim latest" "full latest-full"; do
  set -- $pair
  docker build --target "$1" --build-arg VERSION="$ver" -t "$reg:$2" .
  docker push "$reg:$2"
done
```

`VERSION` всегда без ведущего `v`; Dockerfile отбивает форму `vX.Y.Z` до сборки.

## Релиз

Тег `v*` прогоняет gofmt, vet, тесты с `-race` и govulncheck, затем goreleaser
собирает архивы в черновик; публикует человек. GitHub-зеркало получает те же
архивы. Release notes — секция `CHANGELOG.md` этого тега, срезанная из
`## [Unreleased]` коммитом `release:`.
