Файл документирует мета-инструменты, которые видит клиент, с точными формами
ответов и текстами ошибок.

# Мета-инструменты

Набор выставляет девять инструментов MCP: пять — для работы с нижестоящими
серверами, ещё четыре — для их ресурсов и промптов. Сами нижестоящие
инструменты клиенту не показываются; до них доходят через `invoke_command`.

Четыре инструмента ресурсов и промптов (`list_resources`, `read_resource`,
`list_prompts`, `get_prompt`) отвечают только для сервера, который назвал их в
`expose`; см. [Ресурсы и промпты](#ресурсы-и-промпты) ниже.

| инструмент | назначение |
| --- | --- |
| `list_servers` | инвентарь со здоровьем и тегами |
| `list_commands` | имена инструментов одного или нескольких серверов |
| `describe_commands` | входные схемы названных инструментов |
| `invoke_command` | вызвать один нижестоящий инструмент |
| `invoke_many` | вызвать до 8 независимых инструментов одним запросом |
| `list_resources` | ресурсы серверов, которые их отдают |
| `read_resource` | прочитать один ресурс |
| `list_prompts` | промпты серверов, которые их отдают |
| `get_prompt` | отрисовать промпт с аргументами |

Каждая ошибка ниже возвращается обычным результатом инструмента с
`isError: true` и одним текстовым элементом, текст которого начинается с
`Error: `. Сам вызов MCP при этом не падает.

## list_servers

Вход: `{"filter": "code"}` (`filter` необязателен). Фильтр сравнивается без
учёта регистра с именем, описанием и тегами **до** любого подключения:
отфильтрованный сервер никогда не опрашивается.

```json
{
  "servers": [
    {
      "name": "echo",
      "type": "stdio",
      "enabled": true,
      "healthy": true,
      "command": "echo",
      "tags": ["fixture"],
      "approval": "quarantine"
    }
  ],
  "version": "dev"
}
```

| поле | значение |
| --- | --- |
| `name` | имя сервера |
| `description` | есть, когда в конфигурации задано |
| `hint` | одна строка о том, когда этот сервер — то, что нужно, и с чего начать. Встроенная таблица покрывает серверы, которые знает эта сборка; своё поле `hint` набора главнее неё, а у незнакомого сервера без своей строки ключа `hint` нет вовсе |
| `type` | `stdio` или `remote` |
| `enabled` | из конфигурации; выключенный сервер не опрашивается и показывается как `healthy: true` |
| `healthy` | результат опроса; `false` при битой конфигурации или неудачном подключении. Проба, не дождавшаяся свободного слота, отдаётся `true` и не кэшируется — смотри `unknown` |
| `unknown` | `true`, когда проба не началась (не было свободного слота): `healthy: true` тут значит «не больной», а не «проверен» |
| `error` | текст ошибки опроса, есть при `healthy: false` |
| `isolation` | `bwrap`, когда песочница применена; `без изоляции: <причина>`, когда запрошена, но bubblewrap не стартовал (`onUnavailable: warn`/`allow`); `нет: конфиг отвергнут`, когда у записи есть `_configError`; поля нет только у валидного сервера без блока `sandbox` |
| `url` | у remote-сервера — адрес, собственные секреты сервера замаскированы |
| `command` | у stdio-сервера — первое слово `command`, то есть исполнитель, замаскировано так же |
| `tools` | размер каталога, который набор уже держит, — цифра не стоит похода к серверу; поля нет, пока каталог ни разу не читали |
| `visible` | сколько из `tools` действительно видит этот ключ; есть, только когда список урезали профиль или правило `permissions` до непустой части, — ключу, у которого не осталось ничего, поле не приходит: при `0` оно опускается |
| `approval` | `quarantine`, когда набор сверяет дескрипторы с `tools.lock.json`; у процесса без такой записи поля нет |
| `tags` | из конфигурации, когда заданы |
| `version` | версия сборки прокси |

`env` и `headers` сервера в ответ не попадают никогда: видны только исполнитель
из `command` и замаскированный `url`.

Опросы здоровья идут параллельно, не больше 8 одновременно, с таймаутом 15 с и
кэшем на 15 с, который запоминает и неудачи.

## list_commands

Вход — одна из двух форм:

| вход | выход |
| --- | --- |
| `{"server": "alpha"}` | массив инструментов |
| `{"servers": ["alpha", "beta"]}` | объект с ключами по имени сервера, каждое значение — массив; у упавшего сервера — `{"error": "…"}` |
| `{"prefix": "se"}` | с любой из форм выше: оставить только имена, начинающиеся с префикса (без учёта регистра); без совпадений — `[]` |
| `{"namesOnly": true}` | с любой из форм выше: только имена — массив строк или массивы по серверам. У большого сервера сотни инструментов и десятки КБ каталога; имена стоят примерно шестую часть, а схему одного инструмента даёт `describe_commands` |
| `{"maxBytes": 4096}` | с любой из форм выше: потолок ответа, предел 1048576. В отличие от `invoke_command` и `invoke_many`, у вызовов каталога нет умолчания: без поля или с `0` приходит весь каталог; сверх явного потолка ответ уходит в файл, а маркер говорит, сколько пришло |
| оба | `Error: укажи server или servers, не оба` |
| ни одного | `Error: нужен параметр server или servers` |

`prefix` фильтрует уже прочитанный список при отдаче, поэтому кэш схем не
трогается: следующий вызов без префикса видит все инструменты.

Ключ, выданный с профилем (см. [configuration.md](configuration.md#profiles)),
получает каталог без команд, которые профиль запрещает, — `deny: ["*"]`
оставляет его пустым. Ключ без профиля видит весь набор, как раньше.

С `servers` один `requestTimeout` ограничивает весь вызов, а не каждый сервер.
Серверы опрашиваются параллельно, по восемь зараз.

`{"refresh": true}` (у `list_commands` и `describe_commands`) выбрасывает
кэш списка инструментов и спрашивает серверы заново — не чаще раза в 5 с на
вызывающего и сервер. Вызывающий считается по той же идентичности, что у лимита
частоты: отпечаток его ключа, а у открытого набора — адрес клиента; за прокси
адрес общий, поэтому общим становится и окно. Обновление внутри окна
откладывается: ответ приходит из кэша и несёт `_meta.refreshDeferred` с именами
серверов —
`{"refreshDeferred": "serena: обновление каталога не чаще раза в 5s"}`. Это не
ошибка. Иначе кэш живёт столько же,
сколько соединение: набор сам сбрасывает его, когда нижестоящий сервер присылает
`notifications/tools/list_changed`, поэтому инструмент, появившийся на живом
соединении, виден со следующего вызова без `refresh`.

```json
[
  {
    "server": "echo",
    "name": "echo",
    "command": "echo",
    "description": "Echo the given text back."
  }
]
```

`name` — каноническое поле; `command` повторяет его для клиентов, написанных под
старую форму. `description` есть, когда сервер его предоставляет. Пагинация
проводится до конца, с потолком 20 страниц.

Один упавший сервер не скрывает остальные: его значение — `{"error": "…"}`,
а ошибку инструмент возвращает, только если не ответил ни один.

## describe_commands

Вход: `{"server": "echo", "command_names": ["echo", "nope"]}`; оба поля
обязательны.

```json
{
  "commands": [
    {
      "name": "echo",
      "description": "Echo the given text back.",
      "inputSchema": {
        "type": "object",
        "properties": {"text": {"type": "string"}},
        "required": ["text"]
      }
    }
  ],
  "missing": ["nope"]
}
```

`missing` присутствует всегда и перечисляет имена, которых сервер не
выставляет; они не валят вызов. `outputSchema` появляется, когда нижестоящий
инструмент его объявляет. `maxBytes` действует и здесь и, как у
`list_commands`, только когда задан: пачка схем сверх потолка уходит в файл с
тем же маркером обрезки.

## invoke_command

Вход:

```json
{
  "server": "echo",
  "command_name": "echo",
  "parameters": {"text": "hello"}
}
```

| поле | значение |
| --- | --- |
| `server` | обязательно |
| `command_name` | одно из `command_name` или его синоним `command` (ниже) |
| `command` | синоним `command_name`; `list_commands` отдаёт имя именно в поле `command`, поэтому годится любой из ключей. Оба с разными значениями — ошибка. Клиент видит схему при старте сессии, поэтому после обновления ему нужно перечитать `tools/list` (или начать новую сессию), иначе старый `required: command_name` перебьёт `anyOf` |
| `parameters` | необязательный объект; `null` и пустая строка означают `{}` |
| `timeoutMs` | необязательный предел этого вызова в мс, от 1000 до 600000; `0` или отсутствие — `requestTimeout` набора. Вне диапазона отказ до запуска: `Error: timeoutMs: допустимо от 1000 до 600000 мс` |
| `maxBytes` | необязательный потолок ответа в байтах; по умолчанию 32768, не больше 1048576; `0` означает умолчание. Исключение — инструменты каталога `list_commands` и `describe_commands`: они ничего не режут, пока `maxBytes` не задан |

Аргументы нижестоящего инструмента кладутся **внутрь** `parameters`. Любой
другой ключ верхнего уровня — ошибка, поэтому вызов не может молча уйти с
пустыми аргументами:

```text
Error: лишние ключи: path — допустимые: server, command_name, command, parameters, maxBytes; аргументы инструмента кладутся в parameters
```

Неверный тип JSON называется ключом и видом, без Go-типов:
`Error: ключ server: ожидался тип «строка», получен тип «число»`. Префикс
`аргументы:` появляется только тогда, когда ошибка типа не привязана к
именованному ключу — неизвестное или неверной формы поле верхнего уровня,
например `Error: аргументы: ожидался тип «объект», получен тип «строка»`.

Результат нижестоящего сервера возвращается как есть: `content`,
`structuredContent` и `isError` сохраняются. Если соединение падает до первого
байта ответа (`ErrConnectionClosed`, `io.EOF`, сетевая ошибка), прокси один раз
переподключается, ждёт 250 мс и повторяет вызов. Если ответ уже начал приходить
или инструмент вернул `isError`, повтора нет — результат отдаётся как есть,
чтобы не выполнить side effect дважды. `list_commands` и `describe_commands`
не повторяются: у них свои таймауты. `requestTimeout`, когда задан, ограничивает
один вызов, если только вызов не принёс свой `timeoutMs` — свой главнее. Вызов,
который состоялся, сообщает `_meta.timeoutMs`: предел, под которым он шёл на
самом деле, включая `requestTimeout`; так клиент сверяет свой бюджет с настоящим.
Ключа нет, только когда предела нет вовсе, а отказ до запуска вызова `_meta` не
несёт совсем. Вызов, не уложившийся в срок, падает с названным дедлайном:

```text
Error: таймаут вызова 120000 мс: serena/find_symbol не ответил: context deadline exceeded
```

К одному нижестоящему серверу одновременно идёт не больше четырёх вызовов, и
одиночный `invoke_command` — один из них: слоты те же, что у `invoke_many`. Пятый
вызов ждёт свободный слот, и ожидание идёт в счёт его собственного предела — его
`timeoutMs` или `requestTimeout` набора. Если предел кончился, пока вызов стоял в
очереди, ответ называет очередь, а не апстрим:

```text
Error: нет свободного слота для serena/find_symbol: context deadline exceeded
```

Вызов в этом случае не отправляется, о чём и говорит причина в тексте.

### Лимит частоты

У набора может быть `rateLimit` (см.
[configuration.md](configuration.md#ratelimit)). Вызов сверх лимита
отвергается обычной ошибкой инструмента — `isError: true`, текст начинается с
`Error: `, — сам вызов MCP при этом не падает:

```text
Error: лимит 60 вызовов в минуту для serena/find_symbol, повторите через 980 мс
```

Задержка берётся из той же корзины токенов, что отвергла вызов. Каждый
внутренний вызов `invoke_many` считается отдельно и получает такой же отказ в
поле `error`, поэтому один отказ не скрывает остальные. Проверка идёт до
открытия сессии набора: отвергнутый вызов не доходит до сервера, а в `/stats`
он считается как `throttled`, а не как вызов инструмента.

### Профили

Ключ, выданный с профилем (см. [configuration.md](configuration.md#profiles)),
получает отказ на то, что профиль не разрешает, в той же форме, что отказ
правила, — `isError: true`, `_meta.lazyMcpPolicy: "blocked"`:

```text
🚫 Blocked by mcprig policy: профиль reader не разрешает serena/find_symbol
```

Отказ — результат инструмента, а не обрыв связи: вызов MCP остаётся живым.
Внутри `invoke_many` он попадает в поле `error` своей записи, а остальные
выполняются как обычно. `permissions` проверяются первыми, поэтому команда,
запрещённая правилом, отчитывается его сообщением, а не профилем.
`list_commands` такие команды прячет, а не отчитывается ими. Профиль находится
по отпечатку ключа, не по подписи, а ключ без профиля не фильтруется вовсе.

`describe_commands` фильтруется так же: имя, которое скрывает правило или
профиль, не попадает в `commands`, а оказывается в `missing`, так что каталог его
не выдаёт; вызов по угаданному имени по-прежнему отвергается маркером политики.

### Карантин дескрипторов

Дескриптор инструмента — это `name`, `description`, `inputSchema`,
`outputSchema` и `annotations`. Впервые увидев инструмент, прокси одобряет его
дескриптор сам (`approvedBy: "auto"` в `<data>/sets/<id>/tools.lock.json`) и
вызов проходит. Если дескриптор потом отличается от одобренного — новая версия,
подменённая реализация, — инструмент уходит в карантин: вызов отвергается,
ничего не доходя до нижестоящего сервера, — `isError: true` и
`_meta.lazyMcpPolicy: "quarantine"`:

```text
🚫 Инструмент изменился: serena/find_symbol (одобрен 6f1c2b0e9a4d, сейчас 9b7a10c3f25e); одобрите: mcprig approve --set main serena/find_symbol
```

Хэш — sha256 по канонической записи в том виде, в каком её пишет
`json.Marshal`, а не по сырым байтам ответа: сервер, переставивший ключи, его
не сдвинет. Политика одна и настройки не имеет. Хэшируются ровно эти пять
полей: `title` и `icons` — украшение и карантина не поднимают. Карантину нужен
каталог данных набора (`MCPRIG_DATA_DIR`, его выдаёт панель процессу набора):
запущенный руками `mcprig serve --config …` записей не ведёт, а значит и
карантина у него нет. Отвергается только изменившийся
инструмент: соседи по тому же серверу работают, а внутри `invoke_many` остальные
вызовы идут, тогда как своя запись несёт текст в `error`.

`list_commands` показывает инструмент из карантина, а не прячет его, с пометкой
`"changed": true`. `permissions` и профили проверяются раньше, поэтому при обоих
отказах побеждает их сообщение.

Второе одобрение — за человеком: из панели (кнопка «Инструменты» в строке
сервера) или из CLI:

```bash
mcprig approve --set main serena/find_symbol   # один инструмент
mcprig approve --set main --all                # всё, что сейчас изменилось
```

Карантин переживает перезапуск набора; записи сервера, убранного из набора,
чистятся при следующей сборке конфига набора.

Битый `tools.lock.json` не читается как пустой: набор не трогает файл и
отклоняет каждый вызов, пока запись неизвестна —

```text
🚫 Карантин неизвестен: файл одобрений не прочитан (tools.lock.json не разобран: …) — вызов serena/find_symbol отклонён
```

— пока файл не починят или не уберут. Отсутствующий файл — по-прежнему обычный
старт: первый увиденный дескриптор одобряется. Каждый сервер набора, который
ведёт такую запись, несёт в `list_servers` поле `approval: "quarantine"`, так что
режим виден до первого отказа.

Ответ длиннее `maxBytes` усекается, а полный уходит в файл. JSON-ответ режется
**структурно**, поэтому остаётся одним валидным JSON: сначала укорачиваются самые
длинные строковые значения (значение в 32 байта и короче не трогают), а сам
срез записывается внутрь документа — объект получает ключ `_truncated`, массив —
последний строковый элемент:

```json
{"results": ["…"], "_truncated": "ответ усечён: 149873 байт, полный ответ — /tmp/mcprig-data/tool-out/1f3c9a2b7d4e5f60.txt"}
```

Структурному срезу нужно что укоротить: строки длиннее порога в 32 байта или
массив, у которого можно отрезать хвост. Ответ, собранный из одних коротких
строк и значений, которые не ужимаются, честно урезать нечем, и он уходит в
сырой срез ниже: маркер по-прежнему называет полный ответ, но вызывающий
получает фрагмент, а не JSON-документ. Валидный JSON обещан, только пока в
ответе есть длинные строки.

Ответ, который не является одним JSON-документом, скаляр, больше 8 МиБ или
JSON-документ, в котором нечего укорачивать, режется сыро, по границе UTF-8, и
заканчивается маркером с размерами и файлом:

```text
…обрезанный текст
[обрезано: 32768 из 149873 байт, полный ответ — /tmp/mcprig-data/tool-out/1f3c9a2b7d4e5f60.txt]
```

Ответ с `structuredContent` сериализуется в один JSON-конверт и режется
структурно, как любой JSON: вызывающий получает валидный JSON-текст, а не
структуру; в сыром срезе за маркером идёт ещё строка
`[structuredContent больше maxBytes: полный ответ в файле]`.

Полный ответ пишется с правами `0600` в
`${MCPRIG_DATA_DIR:-$TMPDIR}/tool-out/<случайное>.txt`; каталог создаётся при
первом использовании. Ответ в пределах лимита возвращается как
есть — без файла и маркера. Нечисловой или отрицательный `maxBytes`, как и значение
больше 1048576, — ошибка, как любой другой неверный аргумент.

### Как забрать полный ответ по HTTP

Набор на HTTP отдаёт файл вместо пути — с того же слушателя и за тем же гейтом,
что `/mcp`: bearer-ключ набора, `allowedHosts` и проверка `Origin`. Структурно
усечённый JSON несёт этот адрес внутри `_truncated` (`/tool-out/1f3c9a2b7d4e5f60
(тот же ключ, которым вызван инструмент)`); маркер сырого среза выглядит так:

```text
[обрезано: 32768 из 149873 байт, полный ответ — /tool-out/1f3c9a2b7d4e5f60 (тот же ключ, которым вызван инструмент)]
```

`GET /tool-out/<имя>` отдаёт ответ целиком: `text/plain; charset=utf-8`,
`no-store`, срезы по диапазону поддерживаются (`Range: bytes=0-9` — `206`), `HEAD`
отдаёт длину без тела. Имя — это имя файла без `.txt`, шестнадцать hex-символов;
всё остальное — `404`, как и имя, файла которого уже нет.

Выгрузка старше срока хранения — `410 Gone`: обещание маркера кончилось. Срок
эндпоинт читает один раз при старте: набор, запущенный панелью, получает его из
политики реестра (`transport.toolOutTtl`, панель пишет его из
`MCPRIG_TOOLOUT_TTL` при сборке `servers.json`), процесс, запущенный руками,
читает `MCPRIG_TOOLOUT_TTL` сам (по умолчанию `24h`). Более короткая панельная
чистка может убрать файл раньше; тогда маршрут ответит `404`, а не `410`.

Выгрузка принадлежит ключу, чей вызов её создал: файл `<имя>.owner` хранит
отпечаток этого ключа, и читатель с другим ключом получает `404`, а не `403` —
неверное имя не должно подтверждать, что выгрузка существует. Отзыв или ротация
ключа закрывают его выгрузки для всех; держатель без ключа (открытый набор)
владеет выгрузкой как `anonymous` и читает её так же.

Анонимно эндпоинт не отдаёт никогда, даже в открытом наборе: `/mcp` может
пустить запрос без ключа, выгрузку — нет. Набор на stdio оставляет в маркере путь:
файл лежит на файловой системе самого вызывающего, и слушателя, к которому можно
обратиться, у него нет.

## invoke_many

Вход: `{"calls": [{"server": "echo", "command_name": "echo", "parameters": {"text": "a"}}, …], "maxBytes": 4096}`

| поле | значение |
| --- | --- |
| `calls` | обязателен; от 1 до 8 вызовов, каждый — как один вызов `invoke_command`, вместе со своим `timeoutMs` |
| `maxBytes` | необязательный предел на **каждый** ответ; умолчание и ограничения те же, что у `invoke_command` |

Вызовы идут параллельно. К одному нижестоящему серверу одновременно не больше
4 вызовов (восемь зараз роняли батч), всего — не больше 8; тот же предел на
сервер действует и у одиночного `invoke_command`. Бюджет веера существует,
только когда у набора задан `requestTimeout`: тогда это максимум из него и
`timeoutMs` его вызовов, поэтому вызов, попросивший больше места, не срезается
раньше своего предела. Сам предел вызова применяется после получения слота —
ожидание слота ограничено только бюджетом веера. Без `requestTimeout` бюджета
веера нет, и предел соседа не достаёт вызов, своего `timeoutMs` не принёсший.

Ответ — массив, по элементу на вызов, **в порядке `calls`**, а не в порядке
завершения:

```json
[
  {"ok": true, "server": "echo", "command_name": "echo", "result": "echo:{\"text\":\"a\"}", "ms": 12, "timeout_ms": 120000},
  {"ok": false, "server": "nope", "command_name": "x", "error": "неизвестный сервер \"nope\"", "ms": 0, "timeout_ms": 120000}
]
```

`timeout_ms` называет предел, под которым шёл именно этот вызов, — свой
`timeoutMs` или `requestTimeout` набора; `_meta.timeoutMs` ответа — бюджет веера.
Оба поля отсутствуют только тогда, когда предела нет.

`result` — то же, что вернул бы `invoke_command`: текст одиночного текстового
элемента, иначе весь объект результата, усечённый по `maxBytes`. Упавший вызов —
неизвестный или выключенный сервер, запрет правами, ошибка транспорта, таймаут
или результат нижестоящего сервера с `isError: true` — остаётся на своём месте с
`ok: false` и `error`; остальные вызовы это не затрагивает. У отказа правами
`result` несёт тот же ответ, что отдал бы `invoke_command`: маркер
`🚫 Blocked by mcprig policy: …` в `content` и `_meta.lazyMcpPolicy: "blocked"`.

Невалидный вход валит весь запрос с `isError: true`, и ничего не выполняется:
ноль вызовов, больше 8, лишний ключ внутри вызова, нет `server` или
`command_name` (либо его синонима `command`), `parameters` не объект или плохой
`maxBytes`. Если упали все вызовы, `isError: true` несёт сам ответ; частичный
отказ остаётся данными с `ok: false` у упавших записей.

Вызов, который ждал свободного слота у своего сервера и не дождался, получает
отказ про очередь, а не про вызов:

```text
нет свободного слота у сервера serena (лимит 4): ждали 120000ms, вызов не отправлен: context deadline exceeded
```

## Ресурсы и промпты

Ресурсы и промпты нижестоящего сервера по умолчанию выключены: клиент видит их,
только если конфиг сервера назвал поверхность в `expose` (`"resources"`,
`"prompts"` или обе — см. [configuration.md](configuration.md#expose)).
Неизвестное значение — ошибка конфига, и сервер не стартует: опечатка никогда
не читается как сознательное «ничего не отдавать».

### list_resources / list_prompts

Вход: `{"server": "notes"}` или `{}` (оба поля необязательны; `maxBytes`
тоже, без потолка по умолчанию — как у `list_commands`).

С `server` ответ — массив; без него — объект по именам серверов среди всех
рабочих серверов, отдающих эту поверхность; сервер без `expose` в ответ не
попадает вовсе:

```json
[
  {"server": "notes", "uri": "notes://welcome", "name": "welcome", "mimeType": "text/markdown", "size": 240}
]
```

```json
[
  {"server": "notes", "name": "greet", "description": "приветствие",
   "arguments": [{"name": "who", "required": true}]}
]
```

### read_resource

Вход: `{"server": "notes", "uri": "notes://welcome", "maxBytes": 4096}`.
`uri` — тот, что вернул `list_resources`. Без `maxBytes` потолок 32768 байт,
как у `invoke_command`.

Ответ несёт upstream `contents[]` без пересборки — `uri`, `mimeType` и `text`
или `blob` (base64) — с обрезкой по потолку; маркер называет файл с полным
ответом, а собственные секреты сервера вымарываются, как в любом другом ответе.

### get_prompt

Вход: `{"server": "notes", "name": "greet", "arguments": {"who": "мир"}}`.
`arguments` — карта строка→строка; сообщения upstream возвращаются без
изменений в результате `prompt`.

### Что отвергается

Сервер без нужной записи в `expose` или поверхность, которой у сервера нет
(ответ — `isError: true` с текстом `Error: <сервер>: набор не отдаёт ресурсы —
добавьте "resources" в expose этого сервера`).

### Разрешения

Нового вида правил нет: ресурс адресуется как `resource:<uri>`, промпт — как
`prompt:<name>`, сравнение теми же glob-правилами, и профиль ключа видит ту же
строку:

```json
{"rules": [
  {"pattern": "resource:notes://secret/*", "action": "deny", "message": "secret"},
  {"pattern": "prompt:*", "action": "allow"}
]}
```

Гейт срабатывает до подключения к нижестоящему; отказ возвращает тот же
результат `🚫 Blocked by mcprig policy: …`, что и `invoke_command`. То же
касается листингов: `list_resources` и `list_prompts` показывают только то, что
разрешают правила и профиль ключа, поэтому при `default: deny` каталог пуст,
пока правило не назовёт ресурс или промпт.

## Маскировка секретов

До того как ответ попадёт в счётчики или в `tool-out`, его текстовое содержимое
чистится от секретов самого сервера: значения его `env` и `headers`, в именах
которых есть `key`, `token`, `secret`, `pass`, `auth` или `credential`,
заменяются на `***`. Ведущий `Bearer ` срезается, а значение короче 8 символов
остаётся как есть. `structuredContent` не переписывается — это сломало бы клиентов,
которые его читают. Причина: апстрим повторяет ключ в теле ошибки (tavily
присылает `api_key` в validation details), и этот текст иначе попадал бы в
контекст модели.

## Разрешения

Блок allow/deny проверяется до подключения сервера; см.
[configuration.md](configuration.md#permissions). Запрещённый вызов возвращает:

```json
{
  "isError": true,
  "content": [{"type": "text", "text": "🚫 Blocked by mcprig policy: no destructive SQL"}],
  "_meta": {"lazyMcpPolicy": "blocked"}
}
```

Маркер `_meta.lazyMcpPolicy` — то, что ищут хуки хоста. Правило `deny` прячет
имя и из каталога: `list_commands` его не перечисляет, `describe_commands`
кладёт в `missing`, а `list_servers` не считает в `visible` — ключ никогда не
видит имя, которое не смог бы вызвать.

## Счётчики

Каждый завершённый `invoke_command` — и каждый вызов внутри `invoke_many` —
считается в процессе набора: по клиенту, по серверу и по инструменту, с p50/p95
и кольцом последних вызовов. Результат нижестоящего сервера с `isError: true`
считается провалом. Панель читает это через `GET /stats`; в stdio-режиме те же
счётчики и история пишутся в `$MCPRIG_DATA_DIR/stdio/stats/`, каждый вызов
помечен `stdio` — панели над процессом просто нет.

Метка клиента берётся из `_meta["io.modelcontextprotocol/clientInfo"]` того
запроса, который считается, — это per-request client info из SEP-2575. Формат —
`имя/версия` (`opencode/2.2.6`) или одно `имя`, если версии нет (`mcprig`). Для
stateless HTTP это и нужно: рукопожатия `initialize` там нет, метка едет с
каждым запросом, а не с сессией. Если в `_meta` client info нет, метка откатывается
к транспорту: подпись ключа, если ключ подписан (`PATCH /api/sets/<id>/keys/<keyID>`),
иначе `key:<6 hex от хеша токена>/<product token из User-Agent>` для набора с
ключом, один `User-Agent` без ключа и `unknown`, когда нет ни того, ни другого.
Чтение `/stats` открытого набора без его токена по-прежнему заменяет все метки
на `(аноним)`.
