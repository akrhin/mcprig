Файл объясняет, как процессы стыкуются, почему каждый набор — свой процесс и где
живут здоровье, статистика и OAuth.

# Архитектура

## Слои

```text
MCP client ──HTTP/stdio──▶ set process (mcprig serve) ──stdio/HTTP──▶ downstream MCP servers
                                  ▲
                                  │ spawn, config, /stats
                            mcprig panel
```

| слой | ответственность |
| --- | --- |
| панель | реестр, выдача ключей, надзор, секреты, HTTP API и UI |
| процесс набора | пять мета-инструментов, сессии нижестоящих серверов, здоровье, счётчики, OAuth |
| нижестоящий | дочерний stdio-процесс (по желанию обёрнут в `bwrap` через `internal/sandbox`) или HTTP-точка MCP |

Панель — управляющий слой: она никогда не проксирует трафик MCP. Клиенты
говорят с процессом набора напрямую, на `http://<host>:<port>/mcp` с
bearer-токеном набора (или через stdio, когда клиент запускает `mcprig stdio`).

## Один процесс на набор

`mcprig panel` запускает набор, порождая
`<cli> serve --config <dataDir>/sets/<id>/servers.json` со своей группой
процессов, `MCPRIG_DATA_DIR` и `MCPRIG_SET=<id>`. Следствия:

- падение или перезапуск одного набора не влияет на другой;
- у каждого набора свой порт (9100–9199), bearer-ключ и файл лога;
- набор может работать один под systemd, без панели;
- нижестоящий stdio-процесс — внук панели и живёт в своей группе процессов: при
  остановке набор закрывает свои сессии, и каждая сигналит своей группе —
  `SIGTERM`, короткое ожидание, затем `SIGKILL`, — поэтому сервер, который
  оборачивает работу (`sh -c "npx … & wait"`), забирает детей с собой.

Панель материализует `servers.json` атомарно (`0600`) перед каждым стартом,
поэтому файл на диске всегда тот, что был выдан работающему набору. Старт
проверяет, что порт свободен, порождает процесс, затем ждёт до 15 с, пока порт
примет TCP-соединение.

Политика перезапуска:

| событие | поведение |
| --- | --- |
| код выхода 0 | считается нормальным выходом, перезапуска нет |
| код выхода ≠ 0 | перезапуск через `1s << n`, не больше 30 с и не больше 5 попыток |
| порт так и не открылся | процесс убит, `набор … не поднялся: порт … не слушает` |
| остановка | `SIGTERM` группе процессов, затем `SIGKILL` через 5 с |

Логи дописываются в `sets/<id>/mcprig.log`, ротируются в `.log.1` при 5 МиБ, а
последние 2000 строк держатся в памяти для `GET /api/sets/<id>/logs`.

## Перезагрузка без перезапуска

`SIGHUP` процессу `serve` набора заставляет его перечитать `servers.json` и
ответить файлом `reload.status` рядом с ним:
`{"nonce":"…","generation":N,"at":"RFC3339","applied":[…],"restartNeeded":[…],"error":"…"}`.
Файл пишется атомарно (`0600`), поколение растёт на каждой попытке — это
единственное подтверждение, HTTP-маршрута у процесса нет. Сигнал получает
только процесс `serve`, не его группа: stdio-дети `SIGHUP` не обрабатывают и
обязаны пережить правку соседа. Перед сигналом супервизор кладёт случайный
`nonce` в `reload.request` и принимает лишь ответ с ним, поэтому запоздалый ack
прошлой попытки не сойдёт за ответ этой; рестарт удаляет оба файла, и новый
процесс считает поколения с 1.

Что применяет одна перезагрузка:

| изменение | что происходит |
| --- | --- |
| сервер добавлен | запись создаётся, соединения нет до первого вызова |
| сервер удалён | сессия закрыта, кэш инструментов сброшен |
| `command`, `args`, `cwd`, `url`, `headers`, `env`, `envAllow`, `oauth`, `sandbox` | сессия этого сервера закрывается и поднимается заново с новыми полями на следующем вызове; вызов в полёте к нему получает ошибку, а не дожидается ответа |
| `permissions`, `enabled`, `description`, `tags` | обновляются на месте, сессия и кэш инструментов остаются |
| неизменённый сервер | та же запись, та же сессия, тот же кэш |
| `rateLimit`, `profiles` набора | применяются на месте; `requestTimeout` и `healthMonitor` — константы, которые менеджер пишет в файл и не меняет |
| `authToken`, `authTokens` | применяются на месте: панель подменяет список токенов слушателя при перезагрузке, поэтому выданный или отозванный ключ доезжает без перезапуска. Изменённый одиночный `authToken` — основной ключ набора — у прежних процессов всё ещё попадает в `restartNeeded`, и тогда панель отдаёт `reloadError`, а не выдаёт правку за применённую |
| `host`, `port`, `path`, `type`, `allowAnonymous`, `allowedHosts`, `clientNames` | попадают в `restartNeeded`, в силе остаются прежние значения |

`keyProfiles` применяется на месте: менеджер читает его на каждый запрос, в
отличие от полей слушателя выше. Файл, который не читается вовсе, оставляет
процесс на прежнем конфиге: причина в `error`, `applied` пуст. Каждая попытка
пишет одну строку в лог: `reload: применено N, изменено M, удалено K,
generation G`.

## Ленивые подключения

При старте ничего не подключено. Первый вызов инструмента, которому нужен
сервер, открывает его сессию; последующие вызовы переиспользуют её. Параллельный
первый вызов делит одно установление соединения (single-flight на сервер), а
неудачная попытка повторяется на следующем вызове, а не кэшируется навсегда.

Если нижестоящий сервер закрывает сессию (`ErrConnectionClosed`),
`invoke_command` сбрасывает сессию, переподключается один раз и повторяет вызов.
Вторая неудача возвращается с её причиной.

## Здоровье

`list_servers` опрашивает серверы, открывая сессию, с такими параметрами:

| параметр | значение |
| --- | --- |
| TTL кэша | 15 с, включая неудачи |
| таймаут на опрос | 15 с |
| параллельность | не больше 8 опросов одновременно |

Выключенный сервер не опрашивается и сообщает `healthy: true`: выключен — не то
же самое, что сломан. Сервер с `_configError` сообщает `healthy: false` и текст
ошибки без попытки подключения.

Собственный вид здоровья в панели (`GET /api/sets/<id>/servers`) опрашивает
`list_servers` набора и кэширует ответ на 15 с с защитой single-flight, поэтому
открытие дашборда не множит опросы по вкладкам браузера.

## Статистика

Счётчики живут в процессе набора (`internal/stats`): по клиенту, серверу и
инструменту, с числом вызовов и провалов, суммарными миллисекундами, p50/p95 из
резервуара на 256 выборок и кольцом последних 512 вызовов. В stdio-режиме метка
клиента — `stdio`: транспорт и есть единственный клиент процесса; в HTTP-режиме
она берётся из product-токена `User-Agent` плюс 6-символьного отпечатка
предъявленного ключа. Метки и имена
инструментов ограничены 64 байтами, число счётчиков — 4096 (остальное
схлопывается в `(прочее)`), текст ошибки в кольце — 512 байтами.

Панель счётчики не держит: `GET /api/calls` опрашивает `GET /stats` каждого
работающего набора с таймаутом 2 с и сливает ответы; остановленный набор
читается из сырого журнала на диске за последние 7 суток. Работающий набор,
который не отвечает, сообщается только по id. Токены не считаются, потому что
ответы MCP не несут поля с расходом токенов.

## HTTP-транспорт

Каждый набор отдаёт одну stateless-точку:

- протокол `2026-07-28` на запрос; тот же обработчик отвечает и на старые
  версии протокола;
- `GET`, `POST`, `DELETE` на `transport.path` (по умолчанию `/mcp`);
- `Host` и `Origin` сверяются с `allowedHosts`;
- bearer-токен сверяется с sha256 каждого действующего ключа за постоянное
  число операций на элемент; набор обслуживает весь список действующих ключей,
  а отпечаток вызывающего — значит, его профиль и лимиты — берётся из того
  токена, который совпал;
- ограничение тела запроса 4 МиБ;
- нет таймаута чтения (SSE-поток нельзя обрывать), idle-таймаут 60 с;
- `GET /healthz` публичен, `GET /stats` защищён тем же bearer.

## OAuth

Клиентский поток работает внутри процесса набора и только когда нижестоящий
сервер отвечает 401 или 403. Это поток authorization-code с PKCE; динамическую
регистрацию клиентов, обмен кода и обновление делает MCP SDK (под ним
`golang.org/x/oauth2`).

| пункт | значение |
| --- | --- |
| слушатель редиректа | `127.0.0.1:<callbackPort>`, по умолчанию 8947 |
| redirect URI | `http://127.0.0.1:<port>/callback`, можно переопределить |
| порт по умолчанию | фиксирован намеренно: некоторые серверы авторизации принимают только заранее прописанный URI |
| хранение токенов | `<data dir>/oauth.json` (`0600`), регистрации клиентов в `oauth-clients.json` |
| ключ токена | первые 32 hex-символа `sha256(serverName + "\x00" + serverURL)` |

Слушатель ничего не занимает, пока токен не понадобится. Токены
переживают перезапуск, поэтому обновление не требует браузера снова.

Панель проводит тот же поток для человека у браузера: кнопка **авторизовать** в
строке сервера, ссылка в диалоге, код приходит на `GET /oauth/callback` по
адресу самой панели. После этого панель перезапускает набор: работающий
процесс читает токен только при старте.

## Трассировка

Клиент может прислать W3C `traceparent` в `_meta` своего запроса (SEP-414).
Принимается он только пройдя проверку: версия `00`, 32 hex trace-id, 16 hex
parent-id, 2 hex флагов без `ff`, идентификаторы не нулевые. Битый
отбрасывается молча: вызов идёт без трассы, потому что испорченный заголовок —
не ошибка клиента.

Один `tools/call` даёт один спан `mcp.tool.call` с атрибутами `mcp.tool.name`,
`mcp.server.name`, `mcp.command.name`, `mcp.tool.outcome` (`ok`, `error`,
`blocked` политикой) и `mcp.trace.source` — `client`, если трасса вызывающего
продолжена, или `proxy`, если она начата здесь. Подключение к нижестоящему
серверу — `mcp.server.connect`, перечитывание конфига — `mcp.reload`. В спанах
только имена: ни ключ, ни его отпечаток, ни токен в спан не попадают, поэтому
трасса, присланная клиентом, аудитным доказательством не считается.

`traceparent` клиента становится родителем этого спана, а собственный span-id
уходит нижестоящему серверу в `_meta` каждого `invoke_command`,
`read_resource` и `get_prompt`: трасса вызывающего продолжается через прокси в
сервер. Остальное клиентское `_meta` вниз не передаётся — оно принадлежит
вызывающему, а не нижестоящему серверу.

Спаны уходят по OTLP/HTTP, когда задан `OTEL_EXPORTER_OTLP_ENDPOINT`. Без него
провайдер не ставится: ничего не записывается, соединений не открывается, и
остаётся только проброс `traceparent` на выданных для него идентификаторах.
Переменные — в [configuration.md](configuration.md#трассировка).
