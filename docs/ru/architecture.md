Файл объясняет, как процессы стыкуются, почему каждый набор — свой процесс и где
живут здоровье, статистика и OAuth.

# Архитектура

## Слои

```text
MCP client ──HTTP/stdio──▶ set process (mcprig serve) ──stdio/HTTP──▶ downstream MCP servers
                                  ▲
                                  │ spawn, config, /stats
                            mcprig panel
```

| слой | ответственность |
| --- | --- |
| панель | реестр, выдача ключей, надзор, секреты, HTTP API и UI |
| процесс набора | пять мета-инструментов, сессии нижестоящих серверов, здоровье, счётчики, OAuth |
| нижестоящий | дочерний stdio-процесс (по желанию обёрнут в `bwrap` через `internal/sandbox`) или HTTP-точка MCP |

Панель — плоскость управления: она никогда не проксирует трафик MCP. Клиенты
говорят с процессом набора напрямую, на `http://<host>:<port>/mcp` с
bearer-токеном набора (или через stdio, когда клиент запускает `mcprig stdio`).

## Один процесс на набор

`mcprig panel` запускает набор, порождая
`<cli> serve --config <dataDir>/sets/<id>/servers.json` со своей группой
процессов, `MCPRIG_DATA_DIR` и `MCPRIG_SET=<id>`. Следствия:

- падение или перезапуск одного набора не влияет на другой;
- у каждого набора свой порт (9100–9199), bearer-ключ и файл лога;
- набор может работать один под systemd, без панели;
- нижестоящий stdio-процесс — внук панели, но умирает вместе с группой процессов
  своего набора.

Панель материализует `servers.json` атомарно (`0600`) перед каждым стартом,
поэтому файл на диске всегда тот, что был выдан работающему набору. Старт
проверяет, что порт свободен, порождает процесс, затем ждёт до 15 с, пока порт
примет TCP-соединение.

Политика перезапуска:

| событие | поведение |
| --- | --- |
| код выхода 0 | считается нормальным выходом, перезапуска нет |
| код выхода ≠ 0 | перезапуск через `1s << n`, не больше 30 с и не больше 5 раз |
| порт так и не открылся | процесс убит, `набор … не поднялся: порт … не слушает` |
| остановка | `SIGTERM` группе процессов, затем `SIGKILL` через 5 с |

Логи дописываются в `sets/<id>/lazy-mcp.log`, ротируются в `.log.1` при 5 МиБ, а
последние 2000 строк держатся в памяти для `GET /api/sets/<id>/logs`.

## Ленивые подключения

При старте ничего не подключено. Первый вызов инструмента, которому нужен
сервер, открывает его сессию; последующие вызовы переиспользуют её. Параллельный
первый вызов делит одно установление соединения (single-flight на сервер), а
неудачная попытка повторяется на следующем вызове, а не кэшируется навсегда.

Если нижестоящий сервер закрывает сессию (`ErrConnectionClosed`),
`invoke_command` сбрасывает сессию, переподключается один раз и повторяет вызов.
Вторая неудача возвращается с её причиной.

## Здоровье

`list_servers` опрашивает серверы, открывая сессию, с такими параметрами:

| параметр | значение |
| --- | --- |
| TTL кэша | 15 с, включая неудачи |
| таймаут на опрос | 15 с |
| параллельность | не больше 8 опросов одновременно |

Выключенный сервер не опрашивается и сообщает `healthy: true`: выключен — не то
же самое, что сломан. Сервер с `_configError` сообщает `healthy: false` и текст
ошибки без попытки подключения.

Собственный вид здоровья в панели (`GET /api/sets/<id>/servers`) опрашивает
`list_servers` набора и кэширует ответ на 15 с с защитой single-flight, поэтому
открытие дашборда не множит опросы по вкладкам браузера.

## Статистика

Счётчики живут в процессе набора (`internal/stats`): по клиенту, серверу и
инструменту, с числом вызовов и провалов, суммарными миллисекундами, p50/p95 из
резервуара на 256 выборок и кольцом последних 512 вызовов. Метки клиентов берутся
из `clientInfo` MCP в stdio-режиме и из product-токена `User-Agent` плюс
6-символьного отпечатка предъявленного ключа в HTTP-режиме. Метки и имена
инструментов ограничены 64 байтами; число счётчиков ограничено 4096, остальное
схлопывается в `(прочее)`; текст ошибки в кольце ограничен 512 байтами.

Панель счётчики не держит: `GET /api/calls` опрашивает `GET /stats` каждого
работающего набора с таймаутом 2 с и сливает ответы. Набор, который не отвечает,
сообщается только по id. Токены не считаются, потому что ответы MCP не несут
стандартного поля использования.

## HTTP-транспорт

Каждый набор отдаёт одну stateless-точку:

- `2026-07-28` на запрос, тем же обработчиком отвечая и на старые версии
  протокола;
- `GET`, `POST`, `DELETE` на `transport.path` (по умолчанию `/mcp`);
- `Host` и `Origin` сверяются с `allowedHosts`;
- bearer-токен сравнивается за постоянное время;
- ограничение тела запроса 4 МиБ;
- нет таймаута чтения (SSE-поток нельзя обрывать), idle-таймаут 60 с;
- `GET /healthz` публичен, `GET /stats` защищён тем же bearer.

## OAuth

Клиентский поток работает внутри процесса набора и только когда нижестоящий
сервер отвечает 401 или 403. Это поток authorization-code с PKCE; динамическую
регистрацию клиентов, обмен кода и обновление делает MCP SDK (под ним
`golang.org/x/oauth2`).

| пункт | значение |
| --- | --- |
| слушатель редиректа | `127.0.0.1:<callbackPort>`, по умолчанию 8947 |
| redirect URI | `http://127.0.0.1:<port>/callback`, можно переопределить |
| порт по умолчанию | фиксирован намеренно: некоторые серверы авторизации принимают только заранее прописанный URI |
| хранение токенов | `<data dir>/oauth.json` (`0600`), регистрации клиентов в `oauth-clients.json` |
| ключ токена | первые 32 hex-символа `sha256(serverName + "\x00" + serverURL)` |

Слушатель ничего не занимает, пока токен действительно не нужен. Токены
переживают перезапуск, поэтому обновление не требует браузера снова.
