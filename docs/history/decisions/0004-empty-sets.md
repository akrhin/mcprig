# 0004. Пустой набор: инвариант «≥1 сервер» снимается

- **Дата:** 2026-11-15
- **Статус:** принято 2026-11-16 владельцем («все надо чинить»), реализовано в ветке
  `openchamber/code-review-debts`
- **Связано:** аудит `docs/history/audits/2026-11-15-review-v0.5.1.md` §5,
  issue #2 пункт 5

## Контекст

Набор — это процесс, который отдаёт MCP-клиенту инструменты своих серверов и
мета-тулы (`list_servers`, `list_commands`, `invoke_command`, resources,
prompts). Серверы живут в реестре хоста, набор лишь ссылается на них по имени.

Сейчас реестр требует, чтобы в наборе был хотя бы один сервер, и держит это
требование в четырёх местах:

- `internal/registry/validate.go:359-366` — `servers: []` в теле запроса;
- `internal/registry/validate.go:378-380` — результат сборки без серверов;
- `internal/registry/store.go:399-401` — `DeleteServer` последнего в наборе;
- `internal/manager/api.go:1296-1300` — распознавание отказа по русской
  подстроке `последний в наборе` → 400.

Из этого два тупика:

1. **Нельзя создать набор до сервера.** `POST /api/sets` с одним именем и портом
   отвечает 400 `в наборе должен быть хотя бы один сервер`, а форма «New set»
   сервер выбрать не даёт вообще. Пользователь обязан сначала завести сервер —
   при том что замысел набора обратный: «вот контейнер, положу в него что нужно».
2. **Нельзя убрать последний сервер.** `DELETE /api/servers/<name>` отвечает
   400 `сервер <name> последний в наборе <set>: удалите набор или добавьте
   другой`. Удалить набор — значит потерять его ключ (токен живёт в
   `sets[].keys[]`, показывается один раз при создании) и порт. «Добавьте
   другой» — не действие, а совет.

Живой случай: набор `quasar` под сервер `@quasar/mcp` (документация Quasar для
агентов, stdio через `npx -y @quasar/mcp@latest`, проект задаётся рабочим
каталогом или `--project`). Пользователь завёл набор, положил в него один
сервер и упёрся в баннер: убрать сервер нельзя, набор удалять — жалко ключ.

## Что проверили, прежде чем решать

Запрет — не требование рантайма:

- `mcprig serve` с `"servers": []` стартует: `прокси слушает … servers=0`,
  `/healthz` → 200, `initialize` отдаёт `serverInfo` и `tools.listChanged`,
  мета-тулы работают.
- `BuildSetConfig` (`internal/manager/setconfig.go:66-104`) пустой список не
  отвергает — он просто пишет `"servers": []`.
- UI уже несёт пустое состояние «в наборе нет серверов»
  (`web/app.js:331-332`), но ключ i18n нигде не используется: экран недостижим.

То есть пустой набор — задуманное состояние, а инвариант в реестре с ним
разошёлся.

## Решение

**Разрешить пустой набор.** Набор существует независимо от состава; серверы
подключаются и отключаются в любой момент, в том числе до первого.

Что меняется:

1. `validate.go` — пустой `servers` допустим (убрать оба отказа).
2. `store.go:399-401` — удаление последнего сервера оставляет набор с пустым
   списком, а не отказывает.
3. `api.go:1296-1300` — распознавание по подстроке больше не нужно (этот долг
   закрывается вместе: D7 — маппинг по типу).
4. UI: форма «New set» создаёт набор без серверов; редактор состава набора
   добавляет/убирает серверы из коллекции; пустое состояние показывает
   `setSrv.emptyTitle` с кнопками «добавить сервер» и «удалить набор».
5. Запуск пустого набора разрешён и полезен: клиент получает мета-тулы и может
   сам узнать, что серверов нет (`list_servers` → пустой список).

Что НЕ меняется: ключ и порт остаются у набора; `CanServe` по-прежнему требует
активный ключ; удаление набора по-прежнему уносит ключ (это отдельное решение
пользователя о его наборе).

## Последствия и риски

- **Риск низкий:** запрет ничем в рантайме не подкреплён, а UI уже рассчитан на
  пустой список.
- **Тесты:** `internal/registry/store_test.go:340` `TestDeleteServerRefusesLastInSet`
  превращается в тест «набор остаётся пустым»; тесты валидации на пустой
  `servers` — в положительные.
- **Документация:** `docs/en/panel.md`, `docs/ru/panel.md` (создание набора),
  `docs/en/configuration.md` (описание набора) — снять формулировку «набор
  обязан содержать сервер».
- **Обратная совместимость:** старые реестры читаются как есть; новый код лишь
  допускает то, что раньше отвергалось.
- **Не-цель:** автоматическое удаление опустевшего набора. Набор без серверов —
  законное состояние, а не мусор.

## Отвергнутые варианты

- **Оставить запрет, добавить в баннер действие «удалить набор вместе с
  ключом».** Хуже: пользователь теряет ключ и порт из-за того, что хотел
  поменять один сервер; и это чинит симптом, а не модель.
- **Разрешить удаление, но автоудалять опустевший набор.** Молчаливое удаление
  данных (ключ, порт, история) — не то, чего ждёт человек, нажавший «удалить
  сервер».
