# ponytail-review `v0.6.1..HEAD` (0.6.3)

Дата: 2026-11-17 · Ревизия: 9 коммитов, 65 файлов, +878/−515 · Метод: диф + код
вокруг; сборка, `go vet` и `docs-check.sh` прогнаны, тесты — нет.

**Что делает репозиторий:** один Go-бинарник — MCP-прокси, который за одним
эндпоинтом держит несколько MCP-серверов («набор»), панель управления в том же
процессе и CLI (`serve`, `doctor`, `status`, `warm`, `auth`). Состояние —
файлы в XDG-каталоге (реестр с ключами наборов, `env.json`, `sets/*/oauth.json`),
перезагрузка — файл + nonce + сигнал.

**Какая нагрузка допущена:** один оператор на хосте; панель открыта в LAN с
входом по паролю/OAuth; наборы одновременно обслуживают нескольких агентов
(сессии и субагенты) — десятки `invoke_command` в минуту на набор, плюс опрос
панели раз в 1.5 с; релизы режутся тегом.

## Чинить обязательно

### 1. Тег больше не проходит ни одной проверки — релиз публикуется по голому `go build`

**Что это.** Диапазон удалил `.gitea/workflows/release.yml`, где джоба `release`
шла с `needs: [verify, vuln]`: `gofmt`, `go vet`,
`go test ./... -race -count=1 -p 1`, `govulncheck`. Новый
`.github/workflows/release.yml` гоняет только `go build ./...`
(`.github/workflows/release.yml:41`) и `goreleaser check`; проверки переехали в
`.github/workflows/ci.yml:7-10`, а он висит на `push: branches: [master]` и
`pull_request` — на тег не срабатывает. Остальные воркфлоу тоже мимо:
`codeql.yml` — push в master, PR и расписание; `dependency-review.yml` — только PR.

**В чём проблема.** Между «коммит проверен» и «тег опубликован» нет связи.
Случай: ветка `hotfix` с красным `go test ./...` (пакеты `manager` и `e2e` не
делят порты 9100–9199 — падение ловится только `-p 1`), коммит никогда не был в
master, `git tag v0.6.4 && git push origin v0.6.4` → `gh release create` и
`docker push ghcr.io/akrhin/mcprig:0.6.4-slim` проходят: ни одна джоба на этом
пути тестов не запускает. То же для `govulncheck`: тег публикует код, у которого
уязвимость в зависимостях никем не проверялась.

**Фикс (минимальный).** Три строки в `.github/workflows/release.yml` перед шагом
«Собрать архивы» (`setup-go` там уже есть):

```yaml
      - name: Проверки
        run: |
          go vet ./...
          go test ./... -race -count=1 -p 1
```

**Если пропустить.** Первый же флейк уезжает в релиз и в GHCR; откатывать тег и
образ придётся руками, а «зелёный CI» перестаёт что-либо значить для релиза —
он проверяет другую ревизию.

### 2. Документация обещает проверки и пуш в реестр хоста, которых нет

**Что это.** `docs/en/install.md:21-26` и `docs/ru/install.md:21-26`: «Releases
are cut on a `v*` tag by GitHub … it runs the checks — `gofmt`, `go vet`, tests
with `-race`, `govulncheck` … pushing them to `ghcr.io/akrhin/mcprig` and, when
the registry secrets are set, to the host registry as well»; табличная строка
`docs/en/install.md:18` повторяет то же. Комментарий `.github/workflows/release.yml:2-6`:
«Сборку гоняет Gitea CI по тегу (тесты, govulncheck, goreleaser в Gitea)».

**В чём проблема.** Верно только «goreleaser собирает архивы и публикует
страницу». Проверок в `release.yml` нет (находка 1); в реестр хоста GitHub не
пушит вообще — это делает `.gitea/workflows/images.yml`, и сам
`.github/workflows/release.yml:94-95` это признаёт («Реестр хоста из GitHub
недоступен: login отвечает 403»). Случай: оператор по `install.md` ставит тег,
ждёт образ `0.6.4-full` в реестре хоста, тянет его — образа нет, потому что
Gitea-джоба вышла с `exit 0` при отсутствии `secrets.REGISTRY` или `docker.sock`
(`.gitea/workflows/images.yml:36-44`). Два текста описывают пайплайн, которого
не существует, и читатель ищет тесты в `release.yml`, где их нет.

**Фикс (минимальный).** Переписать оба предложения по факту (или сделать их
правдой находкой 1): «Release archives and the GHCR image come from GitHub on a
`v*` tag; the host-registry images are built by Gitea `images.yml` — a green run
there only means the tag pushed what it could». Снять устаревший комментарий
`.github/workflows/release.yml:2-6`.

**Если пропустить.** Документ врёт про ворота и про артефакт: при первом же «на
хосте старая версия» искать будут в GitHub, откуда в реестр хоста не пушится
никогда.

## Стоит починить

### 3. `images.yml` по `workflow_dispatch` публикует `latest` из произвольной ветки

**Что это.** `.gitea/workflows/images.yml:10` — `workflow_dispatch:` без входов;
`:46` — `ref="${{ gitea.ref_name }}"`; `:51-56` — пушит `:$ver-$target` и
`:$latest`/`:latest-full`.

**В чём проблема.** У ручного запуска нет тега: `gitea.ref_name` — имя ветки,
`ver` получается тем же `sed 's/^v//'`, проверки «это тег?» нет. Случай: из UI
запускают «Образы» на ветке `feat-x` → `ver=feat-x`, в реестр хоста уходят
`feat-x-slim`/`feat-x-full` и перезаписываются `latest`/`latest-full`. Хост,
тянущий `latest-full`, получает нерелизный код без тега; вернуть `latest` на
релиз можно только пересборкой, а job зелёный и в логах ничего нет. Прежний
`.gitea/workflows/release.yml` собирал образы только в джобе `release`, то есть
по тегу, — регрессия приехала вместе с файлом.

**Фикс (минимальный).** Удалить строку `workflow_dispatch:` — образы собираются
по тегу (пересобрать можно `git push --force origin <tag>`). Если ручной прогон
всё же нужен — `if: startsWith(gitea.ref, 'refs/tags/')` на джобе и без пушей
`latest`.

**Если пропустить.** `latest` перестаёт означать «последний релиз», и заметить
это можно только по дайджесту образа.

### 4. `authorize/status` проверяет пару по другим правилам, чем `authorize`

**Что это.** Новый 404-чек `internal/manager/oauth.go:80-92` проверяет только
наличие набора и сервера в реестре; запуск `internal/manager/oauth.go:39-60` —
ту же пару плюс членство сервера в наборе (`:49-57`) и `srv.URL != ""` (`:58-60`).

**В чём проблема.** Одно правило «пара набор/сервер годна» записано в двух
местах по-разному. Случай: сервер `remote` есть в реестре, но удалён из набора
`s2` → `GET /api/sets/s2/servers/remote/authorize/status` отвечает
`200 {"state":"idle"}`, а `POST …/authorize` — `400 "сервер remote не входит в
набор s2"`. То самое «idle выглядит как живой вход», ради которого 404 и
добавляли, осталось для веток «сервер вне набора» и «stdio-сервер без URL».
Вторая половина: панель этот 404 не показывает — `web/app.js:2018` (HEAD) в
`catch` просто перезапускает опрос через 3 с, а `web/app.js:1999` считает
`idle` ожиданием, поэтому при удалённом между POST и опросом наборе диалог
«ждём подтверждения в браузере» крутится бесконечно. Теста на новую ветку нет:
`internal/manager/oauth_test.go:38-42` проверяет только 200 для годной пары.

**Фикс (минимальный).** Один helper
`func (m *Manager) authTarget(setID, name string) (*config.Server, error)` с тремя
проверками (набор, сервер, членство) — им пользуются оба маршрута, дубль уходит;
`URL`-проверку оставить только у запуска. В `pollAuth` на не-2xx показать
`v.message` и погасить поток. Тест: GET по `s9/remote` ждёт 404.

**Если пропустить.** Два соседних маршрута отвечают по разным правилам об одном
и том же объекте, диалог по-прежнему зависает, а 404-ветка умрёт при первом
рефакторинге без единого красного теста.

### 5. Линтер ослеплён на права файлов ровно там, где лежат токены

**Что это.** `.golangci.yml:24-26` — глобальные `gosec` исключения `G301`,
`G302`, `G306` (права каталога и файла шире 0750/0600).

**В чём проблема.** Сегодня их нечем оправдать: все записи состояния идут
`0o700`/`0o600` — `internal/manager/api.go:166,378`,
`internal/manager/runtime.go:222`, `internal/oauth/store.go:55`,
`internal/mcpserver/toolout.go:219,227`, `internal/toollock/toollock.go:112,115`,
`internal/stats/history.go:152,236`, `internal/manager/setconfig.go:156`,
`internal/atomicfile/atomicfile.go:26`. При этом этим же кодом пишутся
`sets/<id>/oauth.json` (OAuth-токены), `registry.json` (ключи) и `env.json`
(секреты). Случай: следующая правка пишет `os.WriteFile(path, tok, 0o644)` или
`os.MkdirAll(dir, 0o755)` — `golangci-lint` в CI зелёный, `nolint` не нужен,
токен world-readable, а в ревью такой диф выглядит безобидно.

**Фикс (минимальный).** Удалить три строки `G301`/`G302`/`G306`; ни одного
`nolint` при этом не требуется. `G304`/`G204` оставить: они про путь из конфига
и запуск сервера, то есть про суть прокси. (M7 из maintainability закрыт в
диапазоне — lint-джоба `.github/workflows/ci.yml:68-83` появилась; эта находка
про содержимое конфига, не про отсутствие линтера.)

**Если пропустить.** Единственная механическая защита от «секрет записан 0644»
выключена навсегда и молча.

## Можно потом

### 6. Джоба `web` в CI замолкает, если нет `node`

`ci.yml:156-162`: нет `command -v node` → `echo "…пропущена"; exit 0`. На
`ubuntu-latest` node есть, поэтому не поломка сегодня, но зелёный результат
означает «не проверяли»: смена образа раннера на self-hosted выключает проверку
синтаксиса панели без единой красной строки. Фикс: убрать ветку (4 строки) —
`node --check` упадёт внятно. Если пропустить — сломанная панель приедет в
master зелёной.

### 7. `git diff | grep -q` под `pipefail` может соврать про Dockerfile

`ci.yml:182`: `if git diff --name-only "origin/${BASE}...HEAD" | grep -qE '^(Dockerfile|…)'`
под `set -euo pipefail`. `grep -q` выходит на первом совпадении, `git diff`
получает `SIGPIPE` (141), `pipefail` отдаёт 141 → условие ложно. Случай: PR
меняет `Dockerfile` и ещё сотню файлов, совпадение в начале вывода — образ не
собирается, джоба зелёная. Фикс: `git diff --name-only … > "$RUNNER_TEMP/changed"`
и грепать файл (плюс одна строка).

## Вердикт

**К следующему тегу — с одной правкой.** Код диапазона почти целиком линт и CI,
логических регрессий в Go нет: сборка, `go vet` и `docs-check.sh` зелёные. Но
ворота релиза сузились с «тесты + vet + govulncheck» до `go build`, а два
документа описывают проверки, которых не существует, — это дешёво чинится
тремя строками (находка 1) и одной правкой текста (находка 2). Находки 3–5 —
до 0.7: ручной прогон образов умеет переписать `latest`, две соседние ручки
расходятся в правилах, линтер выключен на права файлов.

**Экономия:** −9 строк, −0 зависимостей (1 — `workflow_dispatch`, 3 — gosec
excludes, 4 — ветка `web`-джобы, +1 — чтение списка изменённых файлов).

**Не проверял:** полный `go test ./...`, `e2e`, поднятую панель и наборы (гонял
только `go build ./...`, `go vet ./...`, `bash scripts/docs-check.sh` — все
зелёные); сам `golangci-lint` на хосте не установлен, поэтому новая lint-джоба
и все `nolint`-комментарии диапазона прогоном не проверены, версии `v2.15.0` и
action `v9.3.0` не сверены с существующими; SHA-пины экшенов, наличие секретов
реестра и `docker.sock` у Gitea-раннера, публичность GitHub-репозитория (от неё
зависит `dependency-review`); `goreleaser` и `.goreleaser.yaml` (в диапазоне не
менялись); `web/` и `docs/history/index.md` изменены в рабочем дереве и в
диапазон не входят — цитаты строк даны по HEAD.
