## R1. Карантин: битый `tools.lock.json` теряет одобрения и тут же одобряет текущие дескрипторы

`internal/toollock/toollock.go:66-72`:

```go
func Read(path string) File {
	f, err := ReadFile(path)
	if err != nil && !errors.Is(err, fs.ErrNotExist) {
		slog.Warn("tools.lock.json не прочитан — одобрения неизвестны", ...)
	}
	return f
}
```

`Update` (единственный писатель) читает именно `Read`, а не `ReadFile` (`toollock.go:96-107`):

```go
f := Read(path)            // битый JSON → File{Tools: {}}
if !fn(&f) { return nil }
return Write(path, f)
```

`observe` добавляет всё, чего в файле нет, как одобренное (`quarantine.go:38-62`):

```go
case !seen:
	f.Tools[key] = toollock.Entry{Hash: hash, ApprovedAt: now, ApprovedBy: "auto"}
	dirty = true
```

А порядок в `invokeCommand` такой, что обход каталога идёт **до** проверки (`manager.go:1094-1106`): `toolForCall` → при пустом кэше `toolsOf` → `storeTools` → `observe` → только потом `quarantine`.

Итог: файл, который не разбирается (ручная правка, сбой диска, смена формата `Entry` при обновлении), в первом же вызове после старта (кэш пуст) переписывается, все текущие дескрипторы получают `ApprovedBy:"auto"`, и `quarantine` его принимает. Заявленный инвариант («файл не читается — отказ», `quarantine.go:69-76`) выполняется только для ошибки чтения, при которой не удаётся и запись (каталог вместо файла — тест `quarantine_test.go:325-340`), и для «долгоживущего» процесса с непустым кэшем. Теста на битый JSON нет.

**Влияние.** Карантин — единственная защита от подмены дескриптора у уже одобренного инструмента; при повреждении файла он снимается молча (в логе один `Warn`). Для атаки нужен доступ на запись в каталог набора (`0700`, файл `0600`), поэтому это не P1; но при обновлении, меняющем формат записи, каждый набор пройдёт через сброс одобрений — это уже P2.

## R2. `list_servers`: общий бюджет отсутствует, слотов 8, проба 15 с — панель слепнет при массовом зависании

`listServers` (`manager.go:716-761`) запускает по горутине на сервер и зовёт `m.status(ctx, e)`; `callCtx` (общий `requestTimeout`) здесь **не** применяется. `probe` (`manager.go:806-817`):

```go
probeCtx, cancel := context.WithTimeout(ctx, healthTimeout) // 15s
select {
case probeSlots <- struct{}{}:      // 8 слотов на процесс
	...
case <-probeCtx.Done():
```

`maxProbes = 8` (`manager.go:44`), `probeSlots` — `manager.go:77`. Панель (`internal/manager/health.go:24-27,161`) даёт на весь `list_servers` **30 с** (`healthLoadTimeout = 2*healthTimeout`), причём этот бюджет включает и `Connect`.

Арифметика: 16 серверов (текущий реестр) при одновременном зависании — две волны по 15 с = 30 с + коннект ⇒ `session.CallTool` в панели истекает, `healthError` (`health.go:219-224`) ставит **всем** серверам «context deadline exceeded». Уже 9 зависших серверов достаточно, чтобы панель потеряла весь per-server результат. Для прямого MCP-клиента `list_servers` ждёт `ceil(N/8)*15s` (40 серверов — 75 с и больше) без верхней границы.

Комментарий у `probe` («one hung server cannot stall a list») верен только для N ≤ 8 — это расхождение кода с собственным контрактом.

## R3. Порт проверяется не на том адресе

`internal/registry/store.go:695-702`:

```go
func portBusy(port int) bool {
	ln, err := (&net.ListenConfig{}).Listen(context.Background(), "tcp", fmt.Sprintf("127.0.0.1:%d", port))
```

`allocPortLocked` (670-690) и проверка явного порта в `AddSet` (500-502) используют её же. Набор же слушает `listenHost(rt.bindIP)` (`runtime.go:207`, `860-868`) — при заданном `MCPRIG_BIND` это может быть LAN-адрес.

Два следствия: (1) порт, занятый процессом только на `192.168.x.y`, считается свободным → набор создаётся, `portFree` на старте отвечает 409, набор не запускается; (2) порт, занятый только на loopback, считается занятым и пропускается, хотя на LAN-адресе он свободен. Проверка `portFree(listenHost(...))` на старте правильная — расхождение только в реестре/аллокации.

## R4. PUT набора: правка закоммичена, ответ — ошибка

`internal/manager/api.go:1459-1473`:

```go
set, err := m.store.UpdateSet(id, json.RawMessage(body)) // 1459 — запись в registry.json
...
if _, err := m.RestartSet(context.Background(), set); err != nil {
	return err                                           // 1471-1472 — 409/500 клиенту
}
```

Клиент не может отличить «не сохранилось» от «сохранилось, но не применилось»; панель покажет отказ, хотя правка уже в реестре, а набор, возможно, остановлен (`startLocked` вернул конфликт). Тот же файл в соседней ветке (`reloadSetView`, 1475-1480) и `apiKeyIssue` (1780-1785) отвечают 200 с `reloadError` — контракт непоследователен.

## R5. Дубликаты имён серверов в наборе

`internal/registry/validate.go:383-398` копирует `servers` из тела без проверки повторов:

```go
out.Servers = names
```

`config.Load` второй экземпляр не отбрасывает, а помечает (`internal/config/config.go:930-935`):

```go
if seen[srv.Name] { srv.ConfigError = "имя уже занято другим сервером" }
```

В результате `BuildSetConfig` пишет сервер дважды, `list_servers` показывает фантомный «битый» дубль, `publishSchema` перезаписывает запись по имени. Дешевле отбить дубликат в `buildSet`, как это делает `AddServer` для реестра.

## R6. `invoke_many`: агрегатный отказ неотличим от успеха

`invokeMany` всегда возвращает `jsonResult(out)` (`invokemany.go:116`); неуспех несёт только `OK:false`/`Error` в элементе. `invoke_command` на ту же ошибку отвечает `errResult` с `IsError:true` (`manager.go:1655-1660`). Клиент, который маршрутизирует по `isError` (типовой хост), видит полностью провалившуюся пачку как успешный вызов. Описание инструмента (`manager.go:642-670`) говорит «ошибка одного не отменяет остальные», но не фиксирует, что общего `isError` не будет никогда.

## R7. Reload остановленного набора без ключа — 500

`internal/manager/api.go:1545-1558` (ветка «набор не запущен») вызывает `BuildSetConfig`, а она отказывает (`setconfig.go:64-66`):

```go
if set.Token == "" && !set.Open {
	return nil, fmt.Errorf("у набора %s нет активного ключа — выдайте новый", set.ID)
}
```

Набор, у которого отозвали последний ключ (`RevokeKey` → остановка), не может перезаписать `servers.json` этим маршрутом: 500 на действие, которое для остановленного набора безвредно (файл нужен только следующему старту, а старт без ключа всё равно отбивается `CanServe`).

## Проверено: дефекта не найдено

- **`invoke_many` слоты и пределы.** `>8` отбивается до запуска (`invokemany.go:59-61`); на сервер — канал на 4 (`:21`, `:220-243`), слот освобождается `defer` (`:104`), лишние ждут под общим `callCtx` (`:102-110`), дедлок невозможен: под замком `serverSlots.mu` только выдача канала. Ошибка одного вызова не отменяет соседей; порядок сохраняется (`out[i]`). Тесты: `invokemany_test.go:121,155,181,227,249,303`.
- **Изоляция ключей по наборам.** Каждый набор получает только свои `authTokens` (`internal/manager/setconfig.go:82-93`), у каждого свой порт; чужой ключ на порту B получает 401, в том числе в открытом наборе — предъявленный заголовок проверяется всегда (`internal/httplisten/httplisten.go:312-322`). Ключи не покидают панель: `PublicSet` без токенов (`internal/registry/store.go:711-738`), `ExportRegistry` — без ключей (`internal/manager/api.go:992-1015`).
- **Удаление последнего сервера.** Баг `quasar` закрыт: пустой набор — легальное состояние (`internal/registry/validate.go:399-404`), `DeleteServer` чистит состав, набор остаётся с ключом и портом; пустой `serve` стартует (решение `docs/history/decisions/0004-empty-sets.md`).
- **Health/restart/backoff.** `maxRestarts=5`, задержка `1s<<n` с потолком 30 с (`runtime.go:31-32,336-343`), после бюджета — одно событие `set.restart_failed` и остановка; `p.stopping` не даёт `wait` и `startLocked` крутить один и тот же набор; ручной `Start` сбрасывает счётчик (`runtime.go:168-172`). Петли, сжигающей CPU, не видно.
- **Утечки.** Гор routine на вызов ограничены `requestTimeout`; слоты — `defer`; stdio-группы гасятся `groupConn.Close` (3 с → SIGTERM → 1 с → SIGKILL, `internal/downstream/procgroup.go:38-64`); `conn.close` ждёт незавершённый коннект (`manager.go:1820-1842`); выгрузки `/tool-out` чистятся по TTL и объёму (`internal/toolout/toolout.go:124-199`), недописанная пара `.txt/.owner` удаляется (`mcpserver/toolout.go:209-238`).
- **Карантин и переименование.** Новое имя инструмента одобряется автоматически (`quarantine.go:45-47,95-98`) — это заявленное решение, а не дефект; поэтому R1 важен: единственная защита от подмены — сравнение хэшей, и её обнуление при повреждении файла незаметно.

## Наблюдения без блокировки

- `healthCache.get` (`internal/manager/health.go:98-112`): при панике в `load` канал `e.wait` не закрывается, и все последующие `get` для набора ждут до своего `ctx.Done` (панель — 30 с). Нужен `defer` с записью нулевого вида и закрытием канала.
- `Runtime.killPid`/`killGroup` сигналят по числу pid (`runtime.go:592-606`); при переиспользовании pid после `cmd.Wait` возможен сигнал чужому процессу. Для супервизора это классика; закрывается `pidfd`/проверкой времени старта, когда дойдут руки.
- `invoke_many` при отмене клиента пишет в ожидающие вызовы «таймаут вызова 120000 мс» (`invokemany.go:108-110`); для отмены это неверный текст.
- Открытый HTTP-набор получает в маркере усечения локальный путь файла (`mcpserver/toolout.go:86-96`, `cmd/mcprig/main.go` ставит `ToolOutURL` только при наличии токенов): удалённый клиент такой путь не откроет, а `/tool-out` открытому набору закрыт по замыслу.

## Вердикт по 0.7

**К 0.7 — с исправлениями.** P1 нет; архитектура целостна (один агрегат на набор, файл+nonce+сигнал как протокол перезагрузки, fail-closed на старте без ключа, ключи не уходят клиенту). До релиза стоит закрыть два P2: R1 (карантин не должен терять одобрения при битом файле) и R2 (общий бюджет `list_servers`, иначе панель теряет health именно при массовом отказе). R3–R7 — локальные правки, допустимо в 0.7.x; R4/R7 стоит поправить вместе, это один контракт «правка закоммичена → ответ 200 + причина».
