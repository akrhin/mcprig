# 2026-11-16 · Ошибки, которые проглатываются (этап 2 аудита)

- **Объект:** `master`, коммит `846fae1`, mcprig 0.6.3.
- **Метод:** read-only чтение продового кода и карт (`codemap.md`). Сплошной отбор
  кандидатов по формам: `_ = f()`, `if err != nil { return nil }`, `defer … Close()`,
  присвоение `err` без проверки, `json.Unmarshal` в пустоту, обработка
  `context.DeadlineExceeded`/таймаутов, `os.Remove`/`Sync`/`Flush` после работы,
  записи в реестр/`tools.lock.json`/`env.json`/`/tool-out`/health-кэш; затем чтение
  каждого попадания вместе с вызывающим и обработчиком. Сборка, тесты и линт **не
  запускались** — выводы о поведении сделаны по коду.
- **Не дублируется:** R1–R7 (`docs/history/audits/2026-11-16-review-code.md`),
  S-01…S-05 (`2026-11-16-security.md`), M1…M8 (`2026-11-16-maintainability.md`),
  T1…T9 (`2026-11-16-tests.md`). Где находка пересекается с R1, это сказано в строке.
- **Шкала:** P1 — потеря данных/обход защиты без предпосылок; P2 — молчаливый
  провал записи или рестарта, ведущий к работе «не с тем» состоянием; P3 —
  проглатывание, из-за которого причину нельзя назвать; P4 — неверная/неполная
  картина у панели; P5 — гигиена.

## Разборы P2

### E-01. Битый `registry.json` — панель стартует пустой и молчит

`internal/registry/store.go:39-68`:

```go
raw, readErr := os.ReadFile(s.path)
switch {
case readErr == nil:
	var data Data
	if uerr := json.Unmarshal(raw, &data); uerr != nil {
		backup := fmt.Sprintf("%s.corrupt-%d", s.path, time.Now().Unix())
		if rerr := os.Rename(s.path, backup); rerr != nil {
			return nil, fmt.Errorf("реестр %s не разобран: %w. Отложить файл не удалось: %w", s.path, uerr, rerr)
		}
	} else { … }
```

Ошибка разбора не возвращается: файл отложен, `s.data` остаётся `Data{Version: 1, NextPort: FirstPort}`,
`Open` возвращает `nil` error. Единственный потребитель отложенных записей —
`internal/manager/api.go:185-187`, а он читает `store.Dropped()`, куда попадают только
`normalize`/`validateProfiles` (битые id и profiles). Строки «реестр не разобран» нет ни
в одном логе — проверено grep по `corrupt` и по `Dropped()`.

**Почему P2, а не P5.** Данные не потеряны физически (`registry.json.corrupt-<unix>`),
но панель ведёт себя как при пустой установке: пустой список наборов, `CanServe` ложно
для несуществующих наборов, все ключи выдаются заново. Владелец видит «всё пропало» и
действует соответственно — пересоздаёт наборы, раздаёт новые ключи, ломая рабочие
клиенты. Это тот класс, где молчание дороже ошибки.

**Минимальная правка.** `Open` возвращает предупреждение (или кладёт его в `dropped`),
`manager.New` логирует `Error` с путём отложенного файла.

### E-04. Ожидание слота названо «таймаутом вызова»

`internal/mcpserver/invokemany.go:102-110`:

```go
slot := slots.get(e.server().Name)

case slot <- struct{}{}:
	defer func() { <-slot }()
	if err := m.runManyCall(ctx, label, e, c, maxBytes, &ans); err != nil {
		ans.Error = err.Error()
	}
case <-ctx.Done():
	ans.Error = m.timeoutText()
}
```

`timeoutText()` (`216-218`) = `"таймаут вызова %d мс"`. В ветке `ctx.Done()` вызов в
апстрим не уходил вообще: истёк общий бюджет `callCtx` на веере, пока вызов стоял в
очереди к `slots` (`maxPerServer = 4`, `invokemany.go:21`). `invokeCommand` в том же
случае честно говорит `нет свободного слота для %s/%s: %w` (`manager.go:1118-1124`).
Два разных отказа — один текст.

**Сценарий.** Восемь вызовов на один сервер, четыре зависли на медленном инструменте;
остальные получают «таймаут вызова 30000 мс». Диагностика идёт искать медленный
инструмент и `requestTimeout`, а причина — `maxPerServer`.

### E-05. Таймаут без имени сервера и без цепочки

`internal/mcpserver/manager.go:1125-1131`:

```go
res, err := m.callWithRetry(callCtx, labelOf(ctx, req), e, in.CommandName, args)
if err != nil {
	if callCtx.Err() == context.DeadlineExceeded {
		return errResult(fmt.Errorf("таймаут вызова %d мс", m.config().RequestTimeout))
	}
	return errResult(err)
}
```

Текст не содержит ни `srv.Name`, ни `in.CommandName`, ни исходной ошибки: `err` из
`callTool` уже нёс `"<server>: <причина>"` и отбрасывается. Сравнение `==` вместо
`errors.Is` работает для сентинела, но не поймает обёрнутый `DeadlineExceeded`
(например, если `callTool` когда-нибудь начнёт оборачивать `%w`). Рядом, в
`manager.go:1396`, для того же класса используется `errors.Is` — единообразия нет.

**Сценарий.** Клиент видит `Error: таймаут вызова 30000 мс`. Какой из одиннадцати
серверов завис — неизвестно; в логе набора ничего (единственный инструмент диагностики —
`list_servers` post factum).

### E-06. Сбой OpenBao подменяется старым значением секрета

`internal/manager/secrets.go:382-401`:

```go
func (s *Secrets) resolve(name string) (string, string, error) {
	var remoteErr error
	if s.bao != nil {
		v, err := s.bao.get(name)
		switch {
		case err == nil:
			return v, sourceOpenBao, nil
		case errors.Is(err, errSecretNotFound):
		default:
			remoteErr = err
		}
	}
	if v, ok := s.local.get(name); ok {
		return v, sourceFile, remoteErr
	}
	if v, ok := os.LookupEnv(name); ok {
		return v, sourceEnv, remoteErr
	}
	return "", "", remoteErr
}
```

`remoteErr` доезжает до `Secrets.Get` (`297-303`) и выбрасывается — остаётся только в
`remoteErr`-атомике. `startLocked` (`runtime.go:198-206`) читает `rt.sec.RemoteError()`
**только** когда `unresolvedEnvRefs` нашёл отсутствующие имена; при найденном fallback
ветки нет. То есть «OpenBao недоступен, взял из env.json» не попадает ни в статус
набора, ни в `GET /api/sets/<id>`, ни в лог.

**Сценарий.** Ротация токена в OpenBao; на 10 минут хранилище недоступно; набор
перезапускают (или он падает и поднимается). В `env.json` лежит прежний токен — набор
поднимается, health зелёный, все вызовы 401. Причина («использован fallback») видна
только на вкладке env как `remoteError`, то есть после того, как владелец сам туда
заглянет.

### E-07. Сбой удаления в `tool-out` не возвращается

`internal/toolout/toolout.go:160-177,184-197`:

```go
e := entry{filepath.Join(dir, de.Name()), info.Size(), info.ModTime()}
if now.Sub(e.mod) > cfg.TTL && os.Remove(e.path) == nil {
	_ = os.Remove(OwnerPath(e.path))
	rep.Removed++
	…
}
```

`os.Remove`, вернувший ошибку, просто не считается удалённым: `Report.Removed` меньше,
`total` включает файл, `Sweep` возвращает `err == nil`. `sweepAndLog` (`224-232`)
логирует только `err != nil`. Итог: политика retention работает в режиме «сколько
получилось», а выглядит как «работает».

**Сценарий.** Каталог `tool-out` создан прошлым процессом с другим UID (пересборка
образа, смена пользователя сервиса): `EACCES` на каждый `Remove`. TTL не применяется,
потолок 256 МиБ не соблюдается, в журнале — только `tool-out: удалено N` (или ничего).
Диск, на котором уже 97 % занято, заполняется, и падает уже не чистка, а всё остальное.

## Что проверено и признано корректным (положительные примеры)

- **Запись реестра** — `Store.commitLocked` (`internal/registry/store.go:252-264`): сначала
  диск, потом память; `.bak` пишется до основной замены (`writeLocked`, `268-277`);
  ошибка `os.ReadFile` старого файла не глотается (`270-275`).
- **Карантин fail-closed** — `internal/mcpserver/quarantine.go:76-104`: нечитаемый файл и
  ошибка записи дают отказ вызова с названной причиной, а не «наверное, всё в порядке».
- **Частичный отказ по серверам** — `collect` (`internal/mcpserver/resources.go:425-466`) и
  `listCommands` (`manager.go:884-926`) сохраняют место каждого сервера, кладут текст
  ошибки рядом с его именем и отдают общую ошибку, только когда не ответил никто.
- **Выдача ключа** — `deliverKeys`/`apiKeyIssue` (`api.go:1774-1802`): отказ процесса
  доезжает до ответа полем `reloadError`, а не теряется в логе.
- **Закрытие сессии** — `conn.close` (`manager.go:1820-1842`) возвращает ошибку, если
  коннект не завершился за `closeWait`, вместо «закрыто» на веру; `Manager.Close`
  собирает их `errors.Join` (`307-328`).
- **Выгрузка больших ответов** — `spillWriter` (`mcpserver/toolout.go:147-239`): ошибки
  создания/записи/закрытия файла идут наружу, `abort` снимает и файл, и `.owner`;
  `.owner` пишется до тела, чтобы недописанная пара не осталась на диске.
- **Сбой старта ребёнка** — `stderrTail` (`internal/downstream/connect.go:206-229`):
  последние 4096 байт stderr приклеиваются к ошибке, поэтому «bwrap: exec: No such file»
  не превращается в голый `EOF`.
- **Вебхук** — `notifier.send` (`internal/manager/notify.go:117-135`): три попытки,
  последняя ошибка в лог с набором и событием, адрес вырезан (`redactURL`), метка
  перехода снимается, чтобы следующее событие ушло снова.

## Требует обоснования (не находки, но контракт не зафиксирован)

1. **`Reload` сообщает об отказе не ошибкой, а полем.** `Runtime.Reload`
   (`internal/manager/runtime.go:518-546`) на неудачный SIGHUP, смерть процесса и
   неподтверждённую перезагрузку возвращает `(out, nil)`. Все три текущих вызывающих
   (`reloadSetsUsing:2084-2092`, `reloadSetView:1517-1528`, `apiSetReload:1561`) читают
   `out.Error` — но контракт «nil error ≠ успех» нигде не записан и не проверяется
   тестом. Новый вызывающий, написанный по привычке `if err == nil { success }`,
   получит ложный успех. Нужно либо вернуть сентинел-ошибку вместе с `out`, либо
   записать инвариант в doc-комментарий `Reload` и закрепить тестом.
2. **Отсутствие истории статистики.** `cmd/mcprig/main.go:279-284`: `OpenHistory` упал →
   `Warn` и прокси работает. Это осознанно («без неё прокси работает дальше»), но
   `/stats` тогда молча отдаёт снимок без `HistoryStats`, и панель показывает нули за
   дни. Нужно решить: поле `historyUnavailable` в снимке или явный баннер.
3. **`/stats` без профиля (S-04) и каталог без permissions (S-02)** — уже в отчёте
   безопасности; здесь важно, что оба — тоже «показ без ошибки», и фикс в одном месте
   (`stats.SnapshotRedacted`/`filterCommands`) закрывает обе картины.

## Вердикт

**NEEDS FIXES.** Блокеров P1 нет: ни одна находка не даёт обхода защиты и не теряет
данные необратимо. Но три P2 — это ровно те случаи, когда система говорит «готово», а
работает «не с тем»:

1. **E-02/E-03** — правка окружения или секрета отвечает 200, набор остаётся со старым
   значением. Это ложный успех на самом частом действии владельца после ротации ключей.
2. **E-01** — битый `registry.json` превращает панель в пустую установку без единой
   строки в журнале; лечится тремя строками лога и признаком в ответе `Open`.

Остальное — P3/P4: проглатывание причин (E-04…E-07) и неполная картина у панели
(E-08…E-11), их можно закрывать по одной, начиная с E-07 (retention, единственная
находка с накопительным эффектом на диск).

**Ограничения доказательства.** Сборка и тесты не запускались (read-only), поэтому
«поведение» здесь — чтение кода; выводы о частоте сценариев («порт занят», «диск полон»,
«OpenBao недоступен») взяты из того, как код их обрабатывает, а не из журналов хоста.
Ни одна находка не подтверждена воспроизведением на стенде — это следующий шаг для
E-01…E-03 (у каждого есть дешёвый e2e: сломать файл, занять порт, погасить OpenBao).
