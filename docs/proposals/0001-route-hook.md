# 0001. Хук «MCP теперь за mcprig» и очередь улучшений

Status: proposed
Date: 2026-11-09

## Задача

Харнессы (OpenCode, Hermes, что появится дальше) держат список MCP-серверов в
своём конфиге. После переключения агент должен понимать две вещи: **куда**
он ходит за MCP и **почему** имя в конфиге не совпадает с продуктом. Требование
владельца: хук не должен ломать prompt cache.

## Что уже сделано (факт)

- В `~/.config/opencode/opencode.jsonc` ключ `lazy-mcp` указывает на
  `http://192.168.1.92:9101/mcp` (набор `main` панели mcprig), токен — из
  `~/.config/mcprig/main.token`. Контейнер `lazy-mcp` остановлен.
- Ключ оставлен прежним намеренно: маршруты в `AGENTS.md` и скиллах зовут
  `tools["lazy-mcp"]`. Переименование — отдельный шаг, см. вариант B.

## Варианты хука

### A. Ничего не менять

Ключ `lazy-mcp` живёт дальше, за ним mcprig. Агент работает, промпт не меняется,
кэш цел. Минус: имя врёт, диагностика («почему lazy-mcp в docker ps нет?»)
каждый раз требует объяснения.

### B. Переименовать ключ в `mcprig`

Правка конфига + `AGENTS.md` (раздел MCP-топология и синтаксис вызовов) + скилл
`mcp-usage` + ролевые append-файлы. Один прогон, одна инвалидация кэша, дальше
имя правдиво. Минус: пока не обновлены все тексты, агент зовёт несуществующий
`tools["lazy-mcp"]` и получает «No tool named» — ровно та поломка, которую хук и
должен предотвращать.

### C. Плагин-указатель

`~/.config/opencode/plugins/mcprig-route.ts`: на старте сессии дописывает в
system prompt одну неизменную строку.

```
MCP живёт за mcprig: единственный сервер `mcprig` (ключ `lazy-mcp` — легаси-имя),
мета-тулы list_servers / list_commands / describe_commands / invoke_command.
```

Правила кэш-френдливости, без которых плагин вредит:

- строка **константа**: ни времени, ни pid, ни id сессии, ни имени набора;
- не зависит от состояния (никаких «сейчас 11 серверов») — иначе префикс меняется
  и кэш обнуляется на каждом шаге;
- одна точка вставки за сессию, не на каждый запрос;
- ничего не читает с диска в рантайме;
- если строка нужна и другим харнессам — тот же текст в их системный промпт,
  а не отдельная реализация на харнесс.

### D. Двойной ключ на переходный период

`lazy-mcp` и `mcprig` — два коннекта на один и тот же сервер. Отвергнуто: дублирует
схемы в промпте (421 инструмент и так стоит контекста) и плодит два имени для
одного места.

## Рекомендация

B + C одновременно: переименовать ключ и в том же заходе поставить плагин со
строкой-указателем (в ней `mcprig`, а `lazy-mcp` назван легаси-именем ровно на один
релиз). Через релиз строку сократить до одного предложения и убрать упоминание
легаси. Вариант A остаётся рабочим откатом: конфиг-бэкап лежит в
`~/.config/opencode/backups/`.

## Очередь улучшений работы через mcprig

По убыванию пользы на единицу работы. Первые три — про контекст агента, он дороже
всего остального.

1. **Усечение ответов `invoke_command`.** *(закрыто 2026-11-09: `maxBytes`,
   по умолчанию 32768, выгрузка в файл 0600 и маркер; см. `meta-tools.md`)*
   Сейчас ответ downstream уходит целиком:
   один `codebase_search` или `xerj_search` легко даёт 50–200 КБ. Добавить
   `maxBytes` (по умолчанию 32 КБ) и при превышении резать, дописывая
   `[обрезано: N из M байт, полный ответ — /tmp/mcprig/tool-out/<id>.txt]`.
   Агент читает файл сам, если деталь нужна.
2. **Фильтр `list_commands`.** *(закрыто 2026-11-09: поле `prefix`, фильтрация
   на отдаче; теги SDK не отдаёт, поэтому `tags` не делали)* 421 инструмент в
   ответе — это 174 КБ и
   десятки тысяч токенов. У серверов уже есть теги; фильтр по тегу и/или `prefix`
   позволит тянуть только нужное.
3. **Живое обновление схем.** *(закрыто 2026-11-09:
   `ToolListChangedHandler` через `downstream.Connector.OnToolsChanged` сбрасывает
   кэш набора; SDK подписывается, если сервер объявил `listChanged`)*
   `notifications/tools/list_changed` от downstream сбрасывает кэш набора; клиент
   видит новые инструменты без `refresh: true`.
4. **Ретрай только там, где он безопасен.** *(закрыто 2026-11-09: один повтор
   через 250 мс; ответ начался или `isError` — без повтора;
   `list_commands`/`describe_commands` не повторяются)* Разрыв соединения до
   первого байта ответа — повторяем (1 раз, 250 мс); разрыв после начала ответа —
   не повторяем и отдаём ошибку как есть, чтобы не выполнить side effect дважды.
5. **`mcprig doctor`.** *(закрыто 2026-11-09: `cmd/mcprig/doctor.go`, `-json`,
   секреты только именами и источником, код возврата 1 при проблемах; см.
   `docs/{en,ru}/cli.md`)* Одна команда: наборы, ключи, health, версии,
   конфликты портов, доступность `${VAR}` и OpenBao, размер `oauth.json`.
   Заменяет разбор логов панели.
6. **Вес схем в панели.** *(закрыто 2026-11-09: поле `schema` в
   `GET /api/calls?set=<id>` — `schemaBytes`, `schemaTokens` (байты / 4, вверх),
   `tools`; считается из снимка `/stats` набора, то есть из кэша инструментов,
   без походов в downstream; панель показывает это в шапке карточки строкой
   `list_commands`; см. `docs/{en,ru}/panel.md`)* Показать рядом с набором
   «сколько токенов стоит
   `list_commands` по этому набору» — прямая метрика «оптимальной работы»,
   по которой видно, где резать.
7. **Прогрев по таймеру.** `mcprig warm <set>` + `systemd` timer раз в 10 минут:
   первый клиентский вызов всегда тёплый, а не только первые 2 минуты после старта.
8. **`invoke_many`.** Веер независимых вызовов (до 8) одним запросом — агенту не
   нужно 8 round-trip через прокси.
9. **Метка клиента из `_meta`.** *(закрыто 2026-11-09: `labelOf` в
   `internal/mcpserver` берёт `_meta["io.modelcontextprotocol/clientInfo"]`
   запроса, формат `имя/версия` или одно имя; без него — прежний фолбэк на
   ключ/User-Agent/`unknown`; см. `docs/{en,ru}/meta-tools.md`)* SDK шлёт
   `_meta["io.modelcontextprotocol/clientInfo"]`
   в каждом запросе; сейчас stateless HTTP-наборы показывают `(аноним)`, хотя имя
   клиента приходит. Метка вида `mcprig/0.2`, `opencode/2.2`, `hermes/…`.

Сознательно **не** предлагаю: свой кэш ответов инструментов (у каждого downstream
своя семантика свежести), переписывание схем в более компактный формат (сломает
валидацию клиентов), встроенный планировщик в бинарник (systemd уже есть).
