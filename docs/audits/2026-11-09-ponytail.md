# ponytail-audit: весь репозиторий

Дата: 2026-11-09. Репозиторий: `mcp-manager` (рабочий каталог продукта), HEAD `5db4539`.
Аудит только читал код: `internal/`, `cmd/`, `web/`, `deploy/` не изменялись, единственный созданный файл — этот отчёт.
В рабочем дереве на момент аудита уже лежали незакоммиченные правки `README.md` и `internal/mcpserver/manager.go` (healthTimeout 5s → 15s) — они учтены в отчёте.

`What this repo does:` Один статический Go-бинарник, который публикует много MCP-серверов (upstream, протокол Model Context Protocol) через одну точку: четыре мета-инструмента `list_servers` / `list_commands` / `describe_commands` / `invoke_command` вместо загрузки всех инструментов в контекст клиента. Он же менеджер: хранит реестр серверов и «наборов», поднимает на каждый набор отдельный процесс `mcprig serve` со своим портом и bearer-ключом, выдаёт ключи и показывает веб-панель с живым хвостом вызовов. Третий режим — `stdio`: клиент сам запускает процесс, ключ не нужен.

Принятая нагрузка: **один оператор**; панель слушает loopback или стоит за обратным прокси; **1–5 наборов**, в каждом несколько серверов и десятки клиентов; один набор — один процесс на порту 9100–9199. Всё ниже оценено относительно этой нагрузки, не «на миллион пользователей».

Ворота (фактический прогон, рабочее дерево с двумя незакоммиченными файлами):

```
go build ./...                        → без вывода, код 0
go vet ./...                          → без вывода, код 0
go test ./... -race -count=1          → Go test: 169 passed in 13 packages
```

## Must fix

1. **Общий `oauth.json` у всех процессов набора — потеря OAuth-токенов** (`internal/manager/runtime.go:188`, `cmd/mcprig/main.go:162`, `cmd/mcprig/main.go:230`, `cmd/mcprig/main.go:245-257`, `internal/oauth/store.go:113-131`, `deploy/mcprig-set@.service:6`)
   - **Что это:** переменная окружения `MCPRIG_DATA_DIR` задаёт каталог состояния. Менеджер передаёт всем дочерним процессам **один и тот же** каталог (`runtime.go:188`), юнит systemd — тоже (`%h/.local/state/mcprig`), а `mcprig serve` открывает оттуда `oauth.json` и `oauth-clients.json` (`main.go:162`, `stateDir` 245-257). `oauth.Store.Save` (`store.go:113-131`) записывает на диск **весь свой map целиком**.
   - **Проблема:** каждый процесс набора держит свою копию токенов в памяти. Набор A обновил токен (refresh) — записал файл; через минуту набор B сохраняет свой снимок, снятый при старте, и затирает запись A. Конкретно: два набора с OAuth-сервером (gitea, любой логин), серверы обновляют токен по расписанию → после первого же совпадения токен одного набора откатывается к старому; refresh-токен уже прокручен (rotation), поэтому на следующем рестарте нужен новый вход через браузер. Ошибки в логе нет. То же у двух клиентов, запустивших `mcprig stdio` (общий `~/.local/state/mcprig`).
   - **Правка:** в `runtime.go:188` передать каталог набора — `"MCPRIG_DATA_DIR="+filepath.Join(rt.dataDir,"sets",set.ID)` (он уже создан: там `servers.json` и лог), и `Environment=MCPRIG_DATA_DIR=%h/.local/state/mcprig/sets/%i` в `deploy/mcprig-set@.service`. Один тест: два процесса, обе записи, обе читаются после перезапуска.
   - **Если не править:** молчаливая потеря OAuth-токенов при 2+ наборах с OAuth; симптом «отвалился логин» раз в час-сутки, воспроизвести трудно, потому что файл всегда валиден — в нём просто нет чужой записи.

2. **`list_commands` / `describe_commands` без таймаута — мета-инструмент может висеть вечно** (`internal/mcpserver/manager.go:263-275`, `:291-341`, `:362-406`, `:449-454`, `:524-545`)
   - **Что это:** `requestTimeout` из конфига применяется только к самому вызову инструмента (`manager.go:445-451`, `callCtx`), а `commandsOf` (328) и `describeCommands` (378) зовут `m.withSession(ctx, …)` с «голым» контекстом запроса; коннект внутри `invoke_command` тоже идёт с `ctx`, а не с `callCtx` (`:454`).
   - **Проблема:** downstream принял TCP-соединение, но молчит на `initialize`/`tools/list` — зависший `npx`, half-open соединение после сна ноутбука, сервер за мёртвым прокси. `list_commands` ждёт бесконечно: клиент висит, хотя в `servers.json` стоит `requestTimeout: 120000`. `invoke_command` в том же состоянии выходит по таймауту — поведение одинаковых по смыслу операций разное.
   - **Правка:** один хелпер `withTimeout(ctx, m.cfg.RequestTimeout)` и применить его в начале `commandsOf` и `describeCommands`, плюс в `invokeCommand` передавать в `withSession` уже обёрнутый `callCtx` (одна строка `m.withSession(callCtx, …)`). Тест: фейковый downstream, который принимает соединение и молчит, `list_commands` должен вернуть ошибку за `requestTimeout`.
   - **Если не править:** один зависший сервер вешает обзорные инструменты у всех клиентов набора; отличить «медленно» от «навсегда» нельзя.

3. **Правка одной переменной перезапускает все наборы, синхронно** (`internal/manager/api.go:749`, `internal/manager/api.go:762`, `internal/manager/api.go:1289-1302`)
   - **Что это:** `apiEnvPut` и `apiEnvDelete` после записи зовут `m.restartRunning()`, а он гасит и поднимает **каждый работающий набор**, не спрашивая, встречается ли переменная в нём.
   - **Проблема:** `PUT /api/env/DB_PASSWORD` (переменная нужна только набору `db`) роняет сессии клиентов остальных наборов: in-flight вызовы падают, MCP-клиенты видят обрыв. Плюс это синхронно в HTTP-обработчике: `RestartSet` = Stop (до 5 с) + Start (готовность до 15 с), значит при 5 наборах один PUT держит запрос до ~100 с.
   - **Правка:** заменить на `restartSetsUsingEnv(name)` — тот же цикл по `m.store.Sets()`, но с условием, что `envRefs(setServers(set, servers))` содержит `name`; хелперы `serverEnvRefs`/`envRefs` уже есть в `internal/manager/setconfig.go:143-166`. Тест: два набора, правка переменной одного — второй не перезапускался.
   - **Если не править:** любая правка секрета — плановая деградация всех клиентов и подвисшая панель.

## Should fix

4. **Гонка данных на `p.restarts`** (`internal/manager/runtime.go:253`, `:259`; записи — `:141` и `:264`)
   - **Что это:** в горутине `wait` поле `restarts` процесса читается без `rt.mu` (253 — сравнение с `maxRestarts`, 259 — расчёт задержки), а пишется под `rt.mu` в `Start` (`cur.restarts = 0`, строка 141) и в самой `wait` (264).
   - **Проблема:** `-race` этого не видит, окно узкое (между `cmd.Wait()` и ручным `Start`), но гонка настоящая: набор падает в цикле, оператор жмёт Restart ровно в этот момент — задержка backoff считается по устаревшему числу (8 с вместо 1 с) либо потолок `maxRestarts` считается неверно, и набор перезапускается лишний раз.
   - **Правка:** снять снимок под замком в начале `wait` (`rt.mu.Lock(); n := p.restarts; rt.mu.Unlock()`) и дальше читать `n`.
   - **Если не править:** непредсказуемые задержки и счётчик рестартов; при разборе инцидента «почему набор поднимался 40 секунд» ответа нет.

5. **`Store.Dropped()` никто не вызывает — набор исчезает молча** (`internal/registry/store.go:85-128`, `internal/registry/store.go:132-136`; единственный потребитель — `internal/registry/store_test.go:541`)
   - **Что это:** при загрузке `normalize` выбрасывает наборы, у которых id не подходит под `namePattern`, и складывает их id в `s.dropped`. Метод `Dropped()` есть, но менеджер его не вызывает.
   - **Проблема:** `registry.json` после ручной правки или из старого формата содержит набор `Demo Set` (пробел в id) → после рестарта панели набора просто нет: ни строки в логе, ни ошибки в API. Серверы и их ключи остались, описание набора и порт потеряны; оператор не знает, что искать.
   - **Правка:** в `Manager.New` после `registry.Open` — три строки: `for _, id := range store.Dropped() { m.log.Warn("набор выброшен: некорректный id", "id", id) }`.
   - **Если не править:** тихая потеря конфигурации; диагностика — только чтением JSON руками.

6. **Явный `port` не проверяется на занятость в ОС** (`internal/registry/validate.go:335-356`; для сравнения — `internal/registry/store.go:562-582`)
   - **Что это:** порт из тела запроса проверяется только диапазоном (`checkPort`) и занятостью внутри реестра. `allocPortLocked`, который выдаёт порт сам, порт ещё и слушает (`portBusy`) — то есть правило «порт должен быть свободен в системе» применяется в двух местах по-разному.
   - **Проблема:** `PUT /api/sets/demo {"port":9150}`, а 9150 держит чужой процесс → обновление записывается в реестр и возвращает 200, рестарт падает («порт занят»), и падение уходит только в лог (`api.go:1066-1068`). Набор «сохранён и остановлен», причина в ответе не видна.
   - **Правка:** в `buildSet` для явного порта добавить ту же проверку, что в `allocPortLocked` (`portBusy`), вернуть 409 «порт занят процессом»; ошибку рестарта в `apiSetUpdate` отдавать клиенту (см. находку 12).
   - **Если не править:** набор уходит в остановку с непонятной причиной, оператор ищет проблему не там.

7. **`Secrets.Get` — сетевой запрос в OpenBao на каждую переменную, последовательно** (`internal/manager/secrets.go:261-284`; вызовы — `internal/manager/api.go:721-724`, `internal/manager/runtime.go:503-535`)
   - **Что это:** `Get` при каждом обращении делает HTTP GET в OpenBao (таймаут 5 с на запрос), кэша нет. `apiEnvList` и `childEnv` (env при каждом старте набора) зовут его в цикле по одной переменной.
   - **Проблема:** 40 переменных в серверах, OpenBao болен или медленный → `GET /api/env` висит до 40 × 5 = 200 с, старт набора — десятки секунд; следующий запрос опять идёт в сеть.
   - **Правка:** маленький TTL-кэш в `Secrets` (map имя → значение+источник+`expires`, 30–60 с) с инвалидацией в `Set`/`Delete`. Второй вариант — параллельный обход в `apiEnvList`, но кэш убирает и задержку старта набора.
   - **Если не править:** панель «не отвечает» именно тогда, когда OpenBao болен, а старт наборов растягивается.

8. **Cookie сессии без `Secure` за TLS-прокси** (`internal/manager/auth.go:377`; рядом — `:310-315`)
   - **Что это:** `Secure: r.TLS != nil`. Заявленный в README вариант — панель за обратным прокси, где до Go доходит обычный HTTP.
   - **Проблема:** браузер за https-прокси получает `mcp_session` без флага `Secure`, и cookie уйдёт по любому `http://`-запросу к тому же хосту (downgrade, http-редирект). Там же: `clientIP` берёт только `RemoteAddr`, поэтому за прокси все клиенты — один IP, и лимит 5 неудачных логинов в минуту (сам лимит принят) превращается в глобальный выключатель входа: чужой сканер в той же сети блокирует оператора.
   - **Правка:** `Secure: r.TLS != nil || r.Header.Get("X-Forwarded-Proto") == "https"`. Для `clientIP` — брать первый адрес `X-Forwarded-For` только когда явно сказано, что мы за прокси (иначе заголовок подделывается и лимит обходится).
   - **Если не править:** сессия панели уезжает без `Secure` в проде; вход блокируется посторонним трафиком.

9. **`list_commands` со списком `servers` теряет весь ответ из-за одного упавшего** (`internal/mcpserver/manager.go:305-313`)
   - **Что это:** в ветке `len(in.Servers) > 0` ошибка любого сервера сразу возвращается целиком (`return errResult(err)`).
   - **Проблема:** `list_commands {"servers":["a","b","c"]}`, b выключен → клиент не получает ни a, ни c, хотя оба ответили. Пакетный обзор, ради которого инструмент и сделан, бесполезен при одной мёртвой зависимости.
   - **Правка:** собирать `map[string]any`, где значение — массив команд либо `{"error": "…"}` (сверить форму с `docs/en/meta-tools.md`), и возвращать ошибку только если упали все.
   - **Если не править:** клиент вынужден опрашивать серверы по одному и сам склеивать ошибки.

10. **`/restart` сервера перезапускает весь набор** (`internal/manager/api.go:1167-1181`)
    - **Что это:** `POST /api/sets/:id/servers/:name/restart` проверяет, что сервер в наборе есть, и зовёт `m.RestartSet`, то есть гасит и поднимает процесс всего набора.
    - **Проблема:** оператор жмёт «перезапустить сервер b», а обрываются сессии клиентов серверов a и c — у набора один процесс и одно соединение на клиента. Ответ честно содержит `"scope":"set"`, но имя эндпоинта и подпись кнопки обещают другое.
    - **Правка:** убрать отдельный эндпоинт и подпись «перезапустить набор» — это удаление кода. Настоящий per-server restart — новая семантика (перезапуск downstream внутри процесса), не для правки по аудиту.
    - **Если не править:** неожиданные обрывы работы при рутинной операции.

11. **Удаление набора оставляет `servers.json` с bearer-токеном** (`internal/manager/api.go:1074-1087`, `internal/manager/setconfig.go:86-96`, `internal/manager/runtime.go:174`)
    - **Что это:** `DELETE /api/sets/:id` гасит процесс и убирает запись из реестра, но каталог `sets/<id>/` не трогает. В нём `servers.json` (0600) с `authToken` набора и лог.
    - **Проблема:** после `DELETE` в `~/.local/state/mcprig/sets/demo/servers.json` навсегда остаётся полный ключ «удалённого» набора и список upstream-серверов; каталоги копятся с каждым экспериментом. «Удалил набор» на деле означает «удалил только из реестра».
    - **Правка:** после `store.DeleteSet` — `os.RemoveAll(filepath.Join(m.rt.dataDir, "sets", id))` (или удалить только `servers.json`, оставив лог, если он нужен для разбора).
    - **Если не править:** на диске живут отозванные ключи и конфиги; гигиена и требования к секретам нарушены.

12. **Ошибка перезапуска после правки уходит в лог, клиент получает 200** (`internal/manager/api.go:1065-1069`, `:1222-1224`, `:1295-1298`)
    - **Что это:** `apiSetUpdate` (после `PUT /api/sets/:id`) и `apiKeyIssue` перезапускают работающий набор и на ошибке пишут `m.log.Warn`, продолжая отвечать 200.
    - **Проблема:** набор работал, порт после правки занят чужим процессом → ответ 200, в теле `runtime.running:false` и **пустое** `runtime.error` (процесс уже удалён из `procs`, `status` про ошибку не знает). Причина — только в логе панели. То же при выдаче ключа: токен выдан, набор лежит, в ответе нет ни слова.
    - **Правка:** положить ошибку в тело ответа (`"restartError": err.Error()`) в обоих местах; в `apiSetUpdate` можно вернуть ошибку целиком (для `apiKeyIssue` нельзя — токен уже выдан и показан один раз).
    - **Если не править:** «сохранил — а не работает», причина не в UI; оператор идёт в journalctl.

16. **Секрет «возвращается» после удаления из OpenBao** (`internal/manager/secrets.go:321-346`, `:261-284`)

Оператор считает секрет удалённым.
    - **Правка:** при пустом `store` удалять из OpenBao, а если там записи не было — из `env.json`, и возвращать, откуда удалили (`source`).
